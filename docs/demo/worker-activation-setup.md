# Local first activation and receipt recovery

Use Node 24 and PostgreSQL 18 with the same checkout, database namespace and local registry for setup and startup. Follow the [activation review setup](activation-review-setup.md) to publish the account scopes, complete attested financial verification, prepare the operator-reviewed bootstrap descriptors and explicitly install the policy. Set `EAPR_REVIEW_SELECTION_FILE` for control and restart the supervisor with `npm run dev`. Control and worker load the installed policy independently at startup. A policy change requires explicit installation and restart.

The supervisor passes the worker the runtime database credential, worker service credential, fixed loopback source origin, demo source allowlist and a separate source-read credential. Protected verification runs on the control side. The worker reads only the safe installed policy and published artifacts from its configured paths. Its two private routes, `POST /internal/activate` and `GET /internal/receipts/:key`, require the worker service credential. The reviewer browser uses the control API and its local session.

1. Prepare one customer using `POST /api/review/:accountId/prepare` with an empty JSON object. Confirm the returned package is ready and reflects the reviewed scope, capture, plan and expected target version.
2. Explicitly approve that package using `POST /api/review/:accountId/activate`. Use the exact prepared fields from the review guide and a fresh idempotency key. Send the authorized local reviewer cookie and CSRF header.
3. A 200 response contains the worker receipt and `replayed`. Read the applied records through `GET /api/parent/:accountId?asOf=<manifest cutover>` and the standing authority through `GET /api/accounts/:accountId/activation`. The first import stores the scoped originals, metadata, lineage, approved snapshot and activity together. The initial authority has epoch one and includes each manifest cursor, including a stream with cursor zero.
4. For a 202 pending response or uncertain HTTP outcome, retry the exact approval body and key with a currently authorized reviewer session. Control asks the worker for the scoped receipt before attempting publication or application again. A recovered 200 returns the original receipt with `replayed: true`. A 409 `ALREADY_ACTIVE` directs the reviewer to the scoped activation GET.

A pending intent retains its original approval and can apply only under the worker's current installed policy, source semantics and target binding. An exact committed receipt remains recoverable during a policy, registry or source outage. Parent inspection uses current registered scope metadata and is independently available when that registry can be read. A mirror storage failure returns the same 202 pending intent even after the runtime commit. Retry the same approval body and key to recover the receipt and finish mirroring.

The [activation handoff](../progress/2026-11-08/handoffs/b-worker-activation-handoff.md) specifies the private transport and transaction checks. The browser approval workflow and ongoing synchronization are separate work.
