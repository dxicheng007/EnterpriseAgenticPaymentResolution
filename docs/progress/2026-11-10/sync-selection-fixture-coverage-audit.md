## Additional concrete qualification gaps

### 1. Different approval vectors require different immutable captured manifests

The baseline is not adjustable through `capture(identity,page)`. Initialization reads the committed activation, checks every activation baseline cursor against its manifest's `resumeAfter`, checks all contiguous bootstrap members, and keys the lane by source reference and manifest hash (`apps/worker/src/sync/bootstrap.ts:40–86`). Checkpoint baseline cursors remain bound to that manifest (`apps/worker/src/sync/capture-store.ts:149–154`). Advancing capture to 4, delaying one approval, or opening the same lane twice cannot produce distinct approved vectors.

The smallest independent qualification objective is two genuine customer approvals against separately authored fixed-A manifests with different vectors in the same runtime database. Both need their exact captured originals, producer inputs, financial/bootstrap proof, policy/scope selection, reviewer action, A5 receipt and origin. Retain an actual event in the approval window, prove its different per-subject baseline applicability, and initialize/capture each lane through accepted APIs. A complete-cut positive control must cover each subject's own interval; simply giving the newer lane extra data yields the mandated `uncovered_stream` result rather than proof of successful independent baseline selection (`docs/progress/2026-11-10/sync-selection-design.md:68–74`; selection plan `:249,261–262`).

The existing truth verifier accepts manifest-bound contiguous members and validates all financial facts; it does not expose a mutable baseline override (`packages/evaluator/src/fixtures.ts:71–110`). This identifies a new fixture composition/qualification gap, not a demonstrated need to change the evaluator or a claim that a proposed extension will pass. All prefix originals and expectations must be authored before publication; original deliveries shared between manifests must retain identical canonical identities/bytes. The exact new construction/interface needs its own review and qualification. No current factory parameter or approved snapshot should be changed opportunistically by Task 9.

### 2. A genuinely unselected bundled profile requires a multi-profile proof, with shared mapping evidence

The test needs an actual committed bundle containing a profile other than the request-selected profile, with that other profile having no selecting committed approval in the inspected catalog. Another independently approved customer is still enrolled, even if present as an unselected profile elsewhere. Pausing/revoking it does not make it never-selected. The current factory's transient absence check before the second approval is also insufficient: the first artifact contains only one profile and the factory does not return at that point.

The unchanged contracts distinguish full artifact membership from the exact selected profile: `selectedProfile` resolves the request hash, while activation validation checks full required-profile financial coverage (`apps/worker/src/activation-validation.ts:72–74,109–130`). `bindTruth` accepts multiple non-overlapping profiles (`packages/evaluator/src/fixtures.ts:117–130`), and bootstrap preparation passes registered profiles plus reviewed subject expectations (`scripts/prepare-bootstrap-verification.ts:19–32`; `packages/evaluator/src/bootstrap-fixtures.ts:201–248`). These are potential seams, not a qualified multi-profile fixture.

There is a specific obstacle to simply combining the two approved-design profiles. `buildDemoCandidate` uses one agreement citation as the artifact mappings' USD evidence reference and emits one profile (`apps/control/src/demo-candidates.ts:41–53,112–144`). Financial evidence verification checks the artifact's same currency citation against **each profile's own contract facts**, both at manifest time and for event lineage (`packages/evaluator/src/evidence-support.ts:136–138,202,239–258`). The accepted fixture's two agreements have distinct file/citation support (`sync-selection-peer-fixture-design.md:49–61,93`). Choosing either existing single-profile spec and appending the other profile therefore does not supply the latter profile's currency support. Matching USD values alone do not satisfy the check.

An allowed DSL `field` operation is not an established escape from this qualifier: the generic mapping schema permits it for currency (`packages/contracts/src/connector.ts:35–46`), but this protected verifier specifically requires `currency.op === 'constant'` and `currency.value === 'USD'`, then exact mapping equality (`packages/evaluator/src/evidence-support.ts:102–130`). A source-field currency mapping therefore does not qualify through the unchanged evidence verifier, regardless of generic DSL expressiveness.

A properly authored common evidence binding is a different possibility. The existing producer support entries associate each fact/field with a file and literal; normalization does not require different facts to use different files (`packages/evaluator/src/evidence-fixtures.ts:20–27,107–129`). Resolution independently binds those entries to real captured citations (`:285–299`), and `currencySupported` accepts the common citation when it actually resolves the currency field of the current profile's own active contract fact. Thus these inspected shapes do not rule out one authentic shared citation supporting both independently authored contract facts. Its relevant original text, all per-profile term evidence, mappings and bootstrap expectations must be authored consistently before first publication and pass the complete real chain. This is a remaining fixture-evidence feasibility/qualification question, **not a proven requirement for any production proof-interface or producer change**. The demo builder's single-agreement parser may require using existing lower-level spec/profile authoring interfaces for a new shared-evidence construction; it is not authority to edit that builder during the current task.

The smallest follow-up is a separate fixed-A multi-profile construction qualification: independently author genuine evidence supporting the shared mapping citation for every required profile, complete the real financial proof for the full artifact, complete selected-profile bootstrap/reviewer/A5 approval, and demonstrate the additional bundled profile has no selecting import/target/authority. The evaluator resolves support to actual cited source ranges (`packages/evaluator/src/evidence-fixtures.ts:285–299`); support IDs cannot be invented or reassigned. Whether new shared evidence and locally authored spec/profile inputs suffice through unchanged APIs must be demonstrated before release. This audit neither proposes protected-producer changes nor asserts they are necessary.
