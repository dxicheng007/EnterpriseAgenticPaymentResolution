## Recommended ruling

**Phase A may stop with `unsupported_history` once its admitted strict metadata/original-read path positively establishes receipt-only history lacking supported P1 coverage. It need not invoke `readSyncReceipt` or perform its reverse receipt-delivery recovery solely to return that incomplete result.** This is a refusal to certify a complete selection cut, not successful recovery or certification of the whole legacy receipt. Zero proposals and no complete witness, acknowledgment, reconstructed head, or financial novelty assertion follow from this branch.

This interpretation follows the accepted design's explicit distinction: items 4–5 require bounded historical proof for a complete cut, and item 4 expressly makes unsupported legacy receipt-only history incomplete (`sync-selection-design.md:60–74`). The closure supplement states exact delivery admission is required **before a ready cut**, with no waiver from the `GlobalClaim` representation (`sync-selection-closure-interface-clarification.md:43`). The task consumes `readSyncUnit`/`readFinancialOrigins`, requires closure of the helpers actually invoked, and distinguishes unsupported coverage from corrupt existing originals (`task-7-brief.md:5,11–13`). It does not prescribe the inherited receipt-recovery API for the unsupported branch. The preflight itself reserves full reverse validation conditionally: “If Task 7 intends full strict legacy receipt recovery” (`task-7-preflight.md:16,36`).

This is not permission to downgrade a detected contradiction to unsupported. Nor does it relax any successful `readSyncReceipt`/`readSyncCommit` semantics. The older exact receipt-recovery contract remains stricter (`docs/progress/2026-11-10/sync-apply-storage-report.md:7–12`; `docs/superpowers/plans/2026-11-08-contract-freeze.md:218`).

## Actual dependency boundary

`packages/parent/src/sync-store.ts` has three relevant paths:

1. `readFinancialOrigins` (`289–296`) calls the exact scoped activation reader, then `readOrigins` (`216–265`). That validates requested canonical financial rows against index fields, full scope, derived target IDs, source event/version, one shared origin and the corresponding initial/ongoing domain. A sync origin calls `readHistoricalReceipt` (`163–173`), whose `readReceiptCore` (`123–154`) validates receipt and plan canonical bytes/digests, plan hash, activation/artifact/profile/scope, indexed epoch, versions, nonempty financial operations, event/record lists, lineage bindings, before/after snapshots, exact projection and balances. The requested original must equal an operation record. `verifyOldAssociations` (`268–285`) checks both older domains on exact full `(source_ref,event_id)` keys for those original records. It uses `rows.every`, so it does not establish association existence or reverse completeness. It does not decode canonical deliveries.
2. `readSyncUnit` (`486–497`) calls `readValidatedUnit` (`476–482`): exact grant/lane, all flat prior-unit references, target/receipt validation, original reads, replay/coalesced old association checks, and canonical delivery/position/inbox/outcome/member agreement (`341–473`). It does not call `verifyLegacyReceiptDeliveries`.
3. `readSyncReceipt` (`533–538`) and `readSyncCommit` (`518–529`) call `verifyReceiptHistory` (`500–514`). When no owning unit exists, that checks every receipt operation's origin and then calls `verifyLegacyReceiptDeliveries` (`192–214`). Its SQL includes `o.receipt_id = $1 OR (o.source_ref = $2 AND o.event_id = ANY($3))`, including foreign-source reverse associations. It requires exact count/membership, canonical delivery integrity, scope/account, record binding and absence of a simultaneous initial association.

The last query is an additional graph, not a hidden dependency of paths 1 or 2. Runtime005 gives the legacy delivery table PK `(source_ref,event_id)` and no receipt-leading index (`db/runtime/005_sync_apply.sql:41–52`). Runtime006 adds origin/unit constraints, not that index; runtime007 adds the source enrollment index only. Passing source-local exact-key preflight does not admit the last query. A cap alone also does not prove an inexpensive query plan.

## Minimal admissible stopping boundary

Use the existing same-client snapshot and shared budget. A narrow supported branch can stop after all of the following obligations for the deciding facts are met:

- Tasks 5/6 have returned their admitted inputs. Earlier incomplete results propagate without additional reads. Before any Task 7 helper, close and meter **its actual** dependency graph: full bounded keys/scalars, lengths/digests, canonical receipt/plan, owner import and approved snapshot, referenced historical snapshots, requested financial records/origins/domain mirrors, and exact older association keys. Existing source-wide catalog and unit/outcome root admission is not replaced with a guessed selected-account predicate.
- The deciding receipt is reached through a real inspected original (or equivalently sufficient already admitted strict facts), with compatible immutable receipt/plan/snapshot/original bindings validated by the existing strict readers. A bare unmatched receipt row, a plan's event list, or an unchecked missing join is not this proof. Missing/ambiguous origin for an inspected financial record remains invalid. Do not claim that validating one requested original validates every other original or association of that receipt.
- Determine lack of the receipt's owning P1 unit by its exact receipt key, using the existing unique `runtime_sync_units.receipt_id` (`006_sync_apply_repair.sql:158`), and reconcile the observed units/outcomes relevant to the deciding facts. A unit found under a wrong scope/lane/activation, an outcome with broken unit/member/origin linkage, or a contradictory head is invalid, not evidence of harmless legacy. Exact absence is not “no unit in the convenient lane.” A sound receipt-only original with no owning unit is sufficient to show that the required P1 history cannot be certified; there is no need to recover all of its historical deliveries to discover that same absence again.
- Independently validate canonical deliveries and both older association domains for the exact full identities actually inspected on this path, plus additional original/member keys reached. The origin reader's scalar old-association check cannot substitute for raw bytes/content hash, stream/sequence and applicable position/capture binding validation. Where the import selected a first-import event, require its exact association and bootstrap occurrence. P1 acknowledges only via the strict exact outcome/member/underlying origin. For the deciding legacy original, retain its compatible exact old association if present; do not turn helper absence tolerance into a missing-association validity claim or invent a P1 acknowledgment.
- Finish validation of the deciding admitted objects; any known hash/canonical/index/scope/original/delivery contradiction raises `SELECTION_STORAGE_INVALID`. Then return the existing incomplete shape with bounded observed facts and accurate cause identity. Unknown lane/stream/event fields remain null. Do not run classification or construct a ready cut. No additional receipt-recovery helper, reverse enumeration, new DTO, export or index is needed for this branch.

It is unnecessary to finish unrelated, unvisited portions of the source history after this stopping condition solely to certify them as valid. Complete source-global absence and complete delivery-claim admission remain mandatory if execution proceeds to **ready**. A locally validated `ReceiptOrigin` is not a complete selection witness, nor permission to expose partial `GlobalClaim` data as a trustworthy ready cut.

“Missing head with history” in the brief/preflight must be applied to supported P1 history that requires a head, not to the intentionally headless legacy positive fixture. Otherwise it contradicts the explicit unsupported-legacy case and accepted storage fixture. Removing a head from a genuine P1 chain remains storage-invalid. No legacy branch synthesizes a head to resolve this distinction.

## Malformed versus unvisited

- A canonical/index/original/delivery contradiction encountered within an admitted read is invalid, even if the same receipt has no P1 unit. Do not catch strict-reader errors as `unsupported_history`.
- A missing old association is not proven valid by `verifyOldAssociations` returning successfully. First-import association existence is separately mandatory. The proposed legacy stop makes no claim of complete old-association coverage; it therefore need not decide every missing reverse association before refusing the cut.
- A reverse association outside the exact inspected keys, including a wrong-source association discoverable only by receipt inversion, is **unvisited**, not validated and not asserted absent. `unsupported_history` is compatible with subsequently discovering corruption there. If a later full recovery is requested, the unchanged strict recovery path must reject it.
- An overflow or deadline encountered before the stopping proof completes returns the existing limit/timeout result; incomplete is not a reason to bypass admission. DB/cancellation failures retain Task 8's existing mapping. Bounded facts report only observed work, not estimated complete counts.

The accepted documents do not specify a universal priority ordering among multiple faults in objects the adapter has not read. This ruling should not invent one or require a full forensic scan before every incomplete return. Root should explicitly accept this visited-facts boundary. If the desired product behavior instead requires discovery of all reverse receipt corruption before reporting unsupported coverage, that is additional diagnostic work requiring a reviewed bounded reverse query plan; it cannot be silently implemented or justified as existing helper closure.

## Delivery/economic distinction retained

The preflight's conclusion that a valid foreign claim on the same immutable mapped financial event entails the same typed economic key is supported by initial import event-to-record validation (`activation-store.ts:146–166`), P1 event/member validation (`sync-store.ts:176–181,451–472`), and compiler identity construction (`plan-batch.ts:94–100`). It does not erase exact canonical delivery admission or establish a new delivery-only DTO. Receipt event lists include replay occurrences, and all-replay units have no new monetary receipt; neither list membership nor receipt identity proves delivery acknowledgment. Same bare IDs under different sources remain different keys.

No new financial/product behavior is needed for the recommended refusal boundary. Questions about repairing legacy progress, accepting legacy-only acknowledgments, rebuilding frontiers, granting partial-source proposals, or making full reverse recovery a new mandatory diagnostic guarantee remain outside Phase A and require separate owner/user specification as applicable.
