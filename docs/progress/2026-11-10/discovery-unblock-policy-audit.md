## B — generated-account read/verify capability

**Authorities:** `docs/superpowers/plans/2026-11-09-contract-freeze-discovery-verification-capability-interim.md:19–38,42,52`; accepted `docs/progress/2026-11-08/handoffs/v4-orchestration-contract-proposal.md:51,350`; `docs/progress/2026-11-08/handoffs/b-discovery-construction-handoff.md:117–119`; PRD `prdv2.md:157–169,253–287,553–558,573`.

**Resolved rules:**

1. Verify/read-verify only when every candidate profile account is already in the authenticated trusted allow-list and its sources are pinned/authorized. The freeze also permits explicit existing server-owned run/task grants; a captured raw tuple is not itself a mapping to a proposed parent ID.
2. Proposal/finding/tool names cannot create capability. Denied subjects stay inspectable and return `VERIFICATION_SCOPE_REQUIRED` before enqueue or attempt consumption; never silently drop denied profiles.
3. Verification, compilation and sandbox replay do not resolve identity, approve a customer, grant activation, or authorize parent writes. Operator runtime scope publication is explicitly **not** a Discovery verify grant (interim freeze:9).
4. Grants must be server owned and audited independently of proposal text. Current composition derives account capability from the configured reviewer (`apps/control/src/discovery-composition.ts:137,160–166`); current recorded grants use `Grants.allowedAccountIds` plus `SourceReadGrant` (`packages/discovery/src/repository.ts:16`). No generated-ID minting path exists.

**Important distinction:** A generated ID that a trusted operator independently preconfigures into the existing session capability is thereafter an already-trusted account under the interim rule. Its generated origin is not a permanent prohibition. This does **not** establish an implemented operator enrollment workflow, permission to auto-append IDs, or a full dynamic Blocker B solution. Do not substitute `publish-scopes`, broaden shared reviewer capabilities casually, or claim the interim freeze closes B.

**Exact remaining product decision, if full dynamic B is required:** Who may newly confer read/verify-only capability on a proposed scope, and what independently checked association conditions suffice? The freeze expressly excludes that rule; PRD explicit customer approval governs financial activation and cannot answer this separate read authorization question. Source read permission alone does not establish parent-account identity or right to read an existing parent baseline.

**Concise choices for the user, only when reaching this dependent work:**

- **Explicit trusted grant (recommended):** a trusted operator/reviewer explicitly grants the exact source-bound proposed scope read/verify-only access, separately from customer activation. Narrowest new authority; an extra setup/review action is required. Keep access to any existing parent account separately authorized.
- **Automatic bounded candidate grant:** server issues candidate-only verify/read capability after independently validating pinned source membership and exact proposed subject, with separate protection for existing parent records. Less manual work, but introduces a new automated authorization rule whose admissibility and collision behavior must be specified.

Do not treat either new workflow as accepted by this audit. Maintaining only the existing trusted allow-list needs no new decision, but leaves full B open.

**Smallest independent Platform deliverable:** publish exact interim grant provenance and deny checks for Discovery consumers, including no implicit parent read/approval expansion; preserve current fail-closed path. Prepare the narrow proposed grant contract for review without implementing automatic grant creation. A genuinely new dynamic grant path follows the decision, not vice versa.

**Ownership/storage:** Platform owns trusted session/composition/admission policy (`apps/control/src/{local-session,discovery-composition,verification-composition}.ts` and evaluator admission seam); Discovery owns consumers (`packages/discovery/src/{repository,verification-tools,supervisor}.ts`). Contracts edits require shared-path release. No B DDL is required merely to preserve interim behavior. A durable new grant ledger, if selected, needs its own reviewed control schema reservation; do not preallocate a fictional grant schema or use runtime scope tables as a shortcut.

## C — beginRepair, finishRun, requestInvestigation

**Authorities:** accepted orchestration `docs/progress/2026-11-08/handoffs/v4-orchestration-contract-proposal.md:134,162,189–210,220–226,228–257`; promoted contract obligations `docs/superpowers/plans/2026-11-08-contract-freeze-v3-discovery-shapes.md` section “Consumer obligations and verification limits”; `docs/progress/2026-11-08/handoffs/v4-lifecycle-handoffs.md:35,53–54,68–70`; original freeze `docs/superpowers/plans/2026-11-08-contract-freeze.md:255–261`; construction handoff:117.

**Resolved rules:**

- `beginRepair` is coordinator-only. Input is `{investigationId,proposalId,expectedProposalRevision,diagnosticCodes}`. Exact linked unresolved compilation/verification diagnostics must exist; no synthetic diagnostic can unlock repair. Increment the investigation repair round once per accepted step, max two per investigation including source-wide; bind task repair round to its investigation attempt. Never reset task/turn counters or erase investigations. Verification separately remains initial plus at most two repairs per run/account; a repair tool does not reset or consume an invented verifier allowance.
- Repair is a control-state mutation under the existing run → investigation → task lock ordering and exact owner/generation/dispatch/step fences. Claim, counters/revisions, result, stale-link/assessment effects where applicable, and safe activity commit together. Same step replays its saved result; stale proposal revision conflicts. No model or external I/O inside this transaction. Preserve pause/current-authority checks and whole-batch preflight/capacity guarantees.
- `finishRun` is coordinator-only with `{}` input. Completion requires at least one **current** compiled proposal, finished bounded task graph, no unresolved task dependencies and no unresolved server-owned blocker in **any opened investigation or source-wide set**, checked under current run/assessment revisions. Recompute server-owned blocker applicability; omitted aliases, proposals, findings or investigations cannot hide blockers. Captured but uninvestigated accounts remain explicitly outside constructed scope.
- Completion is not protected verification eligibility, review readiness, approval or activation. Do not require a new financial eligibility policy to implement it, or make an assistant `done` imply completion. A compiler artifact or eligible financial report cannot clear discovery blockers. Contradiction-resolution authority is explicitly absent, so this work must not create it.
- `requestInvestigation` is allowed to all roles: `{subject,question,dependencyFindingRefs}` creates a bounded persisted request for the coordinator. Subject must be pinned source or captured raw seller/account tuple and within current grants; references must resolve to authorized exact findings; the owner must pin the request-reference lifecycle without using requests to clear blockers. It creates neither tasks nor grants. At most twenty outstanding requests per task; coordinator delegation still obeys existing task/investigation budgets. Strict contracts already exist in `packages/contracts/src/discovery-construction-tools.ts:268–299` (8,192-byte question, bounded input/result, `{ok:true,requestId}`).

**Current representation gaps:** `db/control/004_discovery.sql:18` excludes `completed`; grants at124–125 omit `repair_count` and `repair_round` although bounded columns exist at35,53. `packages/contracts/src/discovery.ts:216` already includes completed. `packages/discovery/src/roles.ts:9–33` recognizes these tools but does not advertise them. No investigation-request table or production repair/finish implementation exists. `ModelClient` task completion currently remains separate from run completion.

**No material user policy decision is required for the above.** Platform + Discovery should settle routine executor details in the published contract: exact request lifecycle/consumption representation, the calling coordinator's atomic finish transition (avoid requiring it already succeeded before calling finish), task-round binding on existing/new repair tasks, strict result schemas/diagnostic vocabulary, and batched finish/repair conflicts. These are implementation representations constrained by the accepted rules, not permission to reset tasks, delete blockers, bypass budgets or auto-request post-runtime investigation. PRD repair lifecycle (`prdv2.md:370–381`) still requires a reviewer to initiate a runtime-break investigation; the design-time request tool does not override that ingress rule.

**Smallest independent Platform deliverable:** accepted narrow C contract plus one additive control migration: extend the run status CHECK to the already-defined completed state; grant only UPDATE(repair_count) and UPDATE(repair_round); add immutable investigation-request storage and only necessary bounded state transitions if request handling is included. Publish exact app-role grant proof requirements and foreign-key/idempotency/budget invariants. Discovery then implements real tools on its existing supervisor, not a parallel scheduler. Do not advertise tools solely because DDL/types exist.

**Ownership/storage reservation:** Platform reserves/reviews `db/control/010_<reviewed-purpose>.sql` **only after confirming it is still free with root/other owners**; this audit does not reserve it. Control001–009 are immutable, including009 verification-request mappings. Runtime006 is already reserved for sync apply repair; C needs no runtime DDL. ## D — live provider/model/actual-input meter boundary

**Authorities:** PRD `prdv2.md:157–169,183–199,401–409,553–577`; orchestration contract:77–83,179–185,228–232,354; implementation plan `docs/superpowers/plans/2026-11-08-implementation-plan.md:278–295`; original freeze:318–320; construction handoff:120; D4 handoff Blocker D; `docs/progress/2026-11-10/discovery-pr43-pr46-review.md:78–80`.

**Resolved rules:**

1. Provider credentials/client remain in trusted control composition. No model SDK/key/calls in worker; no secret/model/path selection from model arguments or browser. A run pins the configured model identity/policy. Missing config fails unavailable; never substitute scripted output, skip/pass a live test or pretend config availability proves a provider call.
2. Limits are already 8,192 input tokens, 2,048 output tokens and 60,000 ms with bounded request/result envelopes. The live adapter must enforce actual provider/model tokenizer/config limits **before I/O**. Meter the actual prepared provider input, including instructions, messages and tool schema/protocol overhead; cap output in the provider request. Bytes/4 is not a provider ceiling, whether applied to the abstract turn or serialized request.
3. Preserve known actual usage even on normalization/refusal/error paths; interruption retains explicit unknown usage. Timeout does not prove remote cancellation and does not release the unsettled-call permit early. Unknown model outcomes block instead of an automatic retry. Provider cancellation/reconciliation remains honest about what it can prove.
4. Live completion needs actual source-driven A/B artifacts and independent holdouts; neither a new meter interface nor an offline fake client proves this.

**Current implementation:** `packages/discovery/src/model.ts:3–10` has `run(turn)` and existing ceilings. Transport consumes injected `baseUrl/apiKey/modelId/estimateTokens` (`live-model-transport.ts:6–16`) and still estimates serialized input with bytes/4 at133–138. Composition already accepts optional `modelClient` (`apps/control/src/discovery-composition.ts:139`); default remains absent. `scripts/live-build.ts:13–16` explicitly labels its OPENAI_API_KEY check harness/operator-only, so it is not an accepted product environment freeze.

**Remaining decision and what it does not block:** the eventual provider/model identity and user-configured access are not established by these sources. Exact env variable names, a versioned trusted model-policy record, a meter port bound to one prepared request, and an optional AbortSignal API are routine Platform/Discovery design choices; asking the user to design a tokenizer interface is unnecessary. A supported real provider-specific tokenizer/config requires technical evidence for the selected model, not permission to weaken the already fixed ceiling. No financial semantics are implicated.

**Smallest independent Platform deliverable:** publish an offline, provider-neutral control configuration/meter contract with strict fail-closed admission: trusted provider/model identity, supported meter/version binding, preparation of one immutable provider request for both metering and transport, explicit unknown/unsupported meter failure, output cap, usage/error and cancellation semantics. A disabled configuration parser/composition seam can be implemented and tested without a key or provider call; product env spelling may be frozen by the owning root. Keep transport corrections in the existing Discovery owner request; do not repeat that review or mount it early.

**If a live choice becomes necessary:** (1) keep live access disabled while completing the offline configuration boundary (recommended now; respects recorded deferral), or (2) have the user name/configure the intended provider and model, then validate its exact tokenizer/adapter and enable it only after the separate readiness gate. These choices are about actual access, cost and provider selection, not new repair or financial rules. Existing documents cannot select the user's provider account or authorize retrieving its secrets.
