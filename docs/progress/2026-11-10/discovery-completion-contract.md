## Chosen representation and exclusions

Use one additive migration and the existing supervisor. Request content, exact finding references and handling associations are append-only. Derive `pending` versus `delegated` from existence of a handling association; do not introduce a mutable queue status, lease, poller or scheduler. A coordinator optionally attaches one existing request to an ordinary bounded delegation. This gives exact consumption provenance without a new resolve/dismiss tool or a new permission.

A mutable request queue would need additional UPDATE/state transition authority without helping these three tools. Treating model delivery as request consumption would lose whether a request actually caused delegated work. Neither alternative is needed here. Optional request linkage on delegation is an additive representation proposal requiring producer review; it is not already present in the executable delegate schema.

No request dismissal, blocker resolution, reopening of terminal tasks, reviewer action, account enrollment, verification retry allowance, provider call, parent write or automatic investigation after a runtime break is added. PRD runtime-break investigation ingress remains human initiated. A request question is untrusted task content, not an instruction to extend tools or authority.

## Exact control010 storage and grants

The following is the schema contract for the future migration, not an applied migration. Use the existing `:app_role` substitution and schema conventions. Existing 004 constraint name is `discovery_runs_status_check`; verify that catalog name in the migration proof.

```sql
ALTER TABLE discovery_runs DROP CONSTRAINT discovery_runs_status_check;
ALTER TABLE discovery_runs ADD CONSTRAINT discovery_runs_status_check
  CHECK (status IN ('queued','running','paused','blocked','failed','completed'));

GRANT UPDATE (repair_count) ON discovery_investigations TO :app_role;
GRANT UPDATE (repair_round) ON discovery_tasks TO :app_role;

CREATE TABLE discovery_investigation_requests (
  request_id TEXT PRIMARY KEY,
  run_id TEXT NOT NULL,
  requester_task_id TEXT NOT NULL,
  seller_entity_id TEXT,
  source_account_id TEXT,
  question TEXT NOT NULL CHECK (octet_length(question) BETWEEN 1 AND 8192),
  CHECK ((seller_entity_id IS NULL) = (source_account_id IS NULL)),
  UNIQUE (run_id, request_id),
  FOREIGN KEY (run_id, requester_task_id, request_id)
    REFERENCES discovery_tool_steps (run_id, task_id, id)
);

CREATE TABLE discovery_investigation_request_findings (
  run_id TEXT NOT NULL,
  request_id TEXT NOT NULL,
  finding_id TEXT NOT NULL,
  finding_revision INTEGER NOT NULL,
  PRIMARY KEY (run_id, request_id, finding_id, finding_revision),
  FOREIGN KEY (run_id, request_id)
    REFERENCES discovery_investigation_requests (run_id, request_id),
  FOREIGN KEY (run_id, finding_id, finding_revision)
    REFERENCES discovery_finding_revisions (run_id, finding_id, revision)
);

CREATE TABLE discovery_investigation_request_delegations (
  run_id TEXT NOT NULL,
  request_id TEXT NOT NULL,
  coordinator_task_id TEXT NOT NULL,
  delegation_step_id TEXT NOT NULL UNIQUE,
  delegated_task_id TEXT NOT NULL UNIQUE,
  PRIMARY KEY (run_id, request_id),
  FOREIGN KEY (run_id, request_id)
    REFERENCES discovery_investigation_requests (run_id, request_id),
  FOREIGN KEY (run_id, coordinator_task_id, delegation_step_id)
    REFERENCES discovery_tool_steps (run_id, task_id, id),
  FOREIGN KEY (run_id, delegated_task_id)
    REFERENCES discovery_tasks (run_id, id)
);

CREATE INDEX discovery_investigation_requests_task
  ON discovery_investigation_requests (run_id, requester_task_id, request_id);

GRANT SELECT, INSERT ON discovery_investigation_requests,
  discovery_investigation_request_findings,
  discovery_investigation_request_delegations TO :app_role;
```

`request_id` is exactly the server `toolStepId`, so its existing dispatch/name/input hash/generation provenance is reachable without duplicated fence columns. Both subject columns NULL mean source-wide; both populated mean the captured raw tuple, never a parent account. There is deliberately no investigation FK: a request alone must not open an investigation, consume the twenty-investigation budget, or establish financial applicability. Capture membership and current grant checks are mandatory consumer checks. No cascading deletes are allowed.

All three new tables are immutable to the app role. The handling association is one request → one delegation → one created task. One request cannot fund repeated task creation; ordinary unlinked delegation stays available under existing budgets. Foreign keys enforce same-run identities and exact immutable finding revisions. They do not prove role, tool name, captured membership, grants, request/task subject equality or budget; the owner transaction must prove those. No SQL SECURITY DEFINER function or trigger grants additional execution authority.

`pending` means no association exists; `delegated` means exactly one does. There is no `resolved` status. Requests and associations remain after task completion, failure, run completion or restart. Count pending requests for the originating task under the run lock; project all remaining batch inserts before any successful effect, allowing at most twenty. The existing bounded task/round/call limits also bound total history. Do not impose an unmentioned per-investigation request quota or silently prune old rows.

Only the two column UPDATE grants and SELECT/INSERT on the three tables are new. Existing run status/revision and task status/revision grants suffice. No table-wide UPDATE, DELETE, TRUNCATE, DDL, sequences, runtime grants or changes to blocker/assessment grants. App SQL privileges constrain columns and immutability; they do not authenticate a supervisor owner. The owner fencing proof remains an executor obligation.

## Strict shared tool contract

Platform publishes schemas, inferred types, root exports and JSON-schema descriptors in `packages/contracts/src/discovery-construction-tools.ts` and `index.ts`, with focused schema tests. Preserve existing input/result shapes for `requestInvestigation`. Use strict objects, prototype-key rejection, existing Id/Version parsers, canonical safe integers and the full 65,536 canonical UTF-8 byte envelope. No arbitrary exception messages, paths, SQL, truth payloads, credentials or diagnostic prose in failures.

| Tool | Input | Success |
| --- | --- | --- |
| `requestInvestigation` | Existing `{subject,question,dependencyFindingRefs}` | Existing `{ok:true,requestId}` |
| `beginRepair` | `{investigationId,proposalId,expectedProposalRevision,diagnosticCodes}`; diagnostic codes are a nonempty unique lexical set of Id strings | `{ok:true,investigationId,proposalId,proposalRevision,repairRound,diagnosticRefs}`; round is 1 or 2 |
| `finishRun` | Strict `{}` | `{ok:true,runId,status:'completed',observedRunRevision,revision}` |

Publish `BeginRepairInputSchema`, `BeginRepairResultSchema`, `FinishRunInputSchema`, `FinishRunResultSchema` and corresponding types/descriptors. `proposalRevision` in repair success equals the checked input revision; repair does not revise proposal content. `diagnosticRefs` is a unique lexical set of strict `{code,kind:'compile',toolStepId,assessmentRevision}` or `{code,kind:'verification',requestKey,jobId,assessmentRevision}` objects, one server-selected binding per requested code. IDs use Id and revisions use Version; every input code occurs exactly once. This safe provenance lives in the existing immutable terminal step result, not a new ledger or hidden extra result property. The finish observed revision is the locked pre-transition revision; its committed revision is exactly one greater. IDs, result values and request subject are server validated, never authority-bearing model context.

Shared safe failures for these tools are exactly `{ok:false,code}` with codes `DISCOVERY_INVALID`, `DISCOVERY_FORBIDDEN`, `DISCOVERY_CONFLICT`, `DISCOVERY_PAUSED`, `SOURCE_UNAVAILABLE`, `TOOL_RESULT_LIMIT`, `TOOL_FORBIDDEN`, `TOOL_UNAVAILABLE`, plus these narrow additions: `PROPOSAL_REVISION_CONFLICT`, `REPAIR_DIAGNOSTICS_REQUIRED`, `REPAIR_LIMIT`, `INVESTIGATION_REQUEST_LIMIT`. Existing request consumers keep their success shape; extending their failure enum is additive. Missing/out-of-scope references are forbidden or conflict after authorization, never a data-bearing error. Unknown internal/database failures are not reflected verbatim.

Finish may additionally return the strict variant `{ok:false,code:'DISCOVERY_INCOMPLETE',blockerCodes}`. `blockerCodes` is a nonempty unique lexical subset of `TASK_GRAPH_INCOMPLETE`, `TASK_DEPENDENCIES_UNRESOLVED`, `NO_CURRENT_COMPILED_PROPOSAL`, `DISCOVERY_ASSESSMENT_UNRESOLVED`, `DISCOVERY_WORK_IN_FLIGHT`. These are bounded explanatory categories; exact authorized existing findings/tasks/proposals remain in state/detail reads. A category list is not a new blocker-resolution ledger. Shape/role/fence errors use the shared failure first, not this incomplete variant.

Delegate input gains optional `requestId:Id`; all existing fields remain required and retain meaning. Absence preserves existing behavior and success shape. The coordinator cannot nominate a different requester, grants or consumed status. Publish the additive delegate descriptor/type with Platform review; Discovery changes its local validator in the released consumer checkpoint. There is no separate consume tool.

## Owner transaction and complete-batch rules

Every fresh mutation uses the existing dedicated advisory-lock connection and local serialized owner queue. Lock run first, then every affected investigation in lexical ID order, then every affected task in lexical ID order, then step/request/proposal records as needed; activity counter last. Plan the complete lock set before locking a caller task: repair can target an investigation different from the coordinator's source investigation. Do not acquire that target investigation after already locking the coordinator task. Ordinary read/action pools cannot claim, apply, complete or repair scheduler work.

Require a valid local owner token, durable current supervisor generation, exact accepted dispatch, native-ID→toolStepId mapping, name/input hash, ordinal, task attempt/revision, current source authority covering saved run/task ceilings, runnable run, and satisfied caller dependencies. Recheck capture membership transactionally using prepared immutable capture facts. Any external capture/evidence preparation occurs before entering this transaction. Recheck current authority immediately before commit. Pause, owner loss or revocation cannot be bypassed by a saved model context.

Before the first successful effect of any remaining batch, validate all remaining names, roles, shapes, references, canonical result sizes and projected capacities. Project request demand, request consumption, investigation/task demand and repair rounds in ordinal order. A later invalid request, over-capacity delegation, malformed repair or forbidden finish prevents an earlier successful mutation. Do not reserve compile/verification work during a supposedly read-only preflight. Failure recording follows the existing bounded supervisor failure protocol and may persist safe failure/accounting state; it cannot leave successful prefix mutations.

`finishRun` must be the only tool call in its accepted dispatch batch. Reject any mixed finish batch before effects as `DISCOVERY_CONFLICT`; this avoids terminal completion stranding later calls or making a model-selected prefix implicitly authoritative. Permit at most one `beginRepair` per target investigation in a batch; repeated target repair is a conflict before effects. A repair followed by delegation to that subject uses the projected new repair round; a preceding delegation to that subject makes repair preflight fail unless that newly projected task is safely rebindable under the rule below. Keep the same projection and recheck at each actual effect; a once-successful preflight is not a reservation across intervening commits.

Fresh control effect, row/counter/revision changes, step result and allowlisted activity commit together. Same authorized terminal step replays its parsed stored result before checking fresh budgets/current proposal CAS; changed step name/input conflicts. Replay performs no mutation, including after run completion or a later proposal revision. It does not leak saved results after grant revocation. If commit outcome is unknown, reconnecting an ordinary pool cannot claim success: replacement owner inspects the existing exact step under current authorization. No fresh step/key is synthesized to retry an uncertain effect.

## requestInvestigation and consumption

1. Validate the existing strict input and current caller authority. Source-wide requests require source-wide capability; an account request must name an actual pinned captured raw tuple covered by current and saved task/run grants. A task cannot request an otherwise unauthorized sibling account as a way to widen scope.
2. Every dependency finding reference must resolve to the exact immutable same-run revision and pass the existing authorized finding-read/evidence checks. An exact older revision remains readable provenance, not an assertion that it is current. Reject missing, duplicate, cross-run or unauthorized refs atomically. Nothing in a reference clears its sticky origin.
3. Under owner locks project the twenty-pending-per-task bound and full success envelope, then insert request and finding rows, persist success on the same step, increment normal caller/run revisions, and emit only safe tool/activity identifiers and counts. Do not open an investigation, increment specialist/repair/verifier counters, create dependencies or enqueue model work here.
4. Supply pending request summaries only to the currently authorized coordinator through server-built bounded turn context: requestId, requesting taskId, source subject, question and exact finding refs, with an explicit total and `hasMore` if a bounded prefix is supplied. Use deterministic requestId ordering and the existing turn/token limits; never silently imply that the prefix is all work. Reconstruct unconsumed rows on later coordinator turns. A single request that cannot fit fails bounded turn admission rather than being silently dropped. No additional model call budget or coordinator task is created to deliver it.
5. `delegateTask` with `requestId` checks the same-run pending row, coordinator role, current grants for request refs, and exact subject equality with the proposed child. The question may be a focused coordinator question; stored original remains immutable. Create the child and association in the ordinary delegation transaction, and inherit the request's exact finding refs into that child's server-built context. Preserve ordinary explicit task dependencyIds; finding refs are not automatically converted into task edges. Child grants derive from existing policy, never from the request. All existing 20+1/10-task/8-round/9-attempt limits still apply.
6. Failed or rolled-back delegation leaves the request pending. Replaying the same delegation step returns the same child/association. Attempting a second distinct delegation step for an already consumed request conflicts; same-step replay cannot count capacity again. Grant revocation denies access/handling without erasing the request. There is no cancellation, dismissal, implicit consumption by reading, or status reset.

A request is an organizational question, not by itself a server-owned financial blocker or a task dependency. This contract does not add “zero pending requests” to the accepted finish predicate. Outstanding requests remain durable and distinguishable from delegated tasks, including after completion; their subjects must not be presented as constructed by merely having requested them. Any actual finding/capture/authorization blocker and every already opened investigation remains in the finish assessment independently. Choosing to delegate a request adds ordinary graph work and its real blockers. A future product requirement for explicit triage/dismissal or mandatory handling needs its own contract; this implementation must not claim it exists.

## Diagnostic applicability and supersession

Use one SQL-only selector under the locked run for repair diagnostic admission and the compile-diagnostic portion of finish. Its outputs distinguish unresolved compile outcomes, repair-selectable codes, historical/superseded observations and uncertainty. Do not implement finish by querying only `discovery_proposal_current` or `discovery_proposal_assessments`: `settleCompileStep(..., {linkCurrent:false})` persists `discovery_compile_steps.result` without putting the failed compiler codes in either current table. Empty current assessment codes therefore do not prove absence of known compiler diagnostics.

**Chronology and historical provenance.** Each attempt's order is the **first** committed `tool.called` control `activity_events.sequence` for its exact `(runId, toolStepId, toolName)`. Use the minimum matching sequence for that attempt, then compare attempts by that number. This event is emitted atomically with actual admission. Existing verification reservations have no per-request attempt-number column; neither task-local attempt numbers, settlement time, UUID ordering nor repeated recovery activity substitutes for admission order. Validate the corresponding dispatch/step and exact compile or verification association; missing or contradictory chronology is uncertainty and fails closed. This contract relies on the current no-pruning activity policy and does not authorize retention changes. Never change retained proposal/assessment revisions, payloads, original codes or activity to express supersession.

**Compile selection key.** The diagnostic lineage key is `(runId, proposalId, complete pinned DiscoveryBinding)`. The exact input subkey is `(proposalRevision, proposalPayloadHash, ordered profileHashes)` obtained from the immutable proposal and `source_payload`; the complete binding includes company/source and manifest/snapshot IDs and hashes. `assessmentRevision`, `observedRunRevision`, task and toolStepId are provenance, **not separate supersession partitions**. A proposal retains its server-owned investigation union, so dropping an alias cannot move this lineage out of the finish scope.

Enumerate every compile row for every proposal in any opened investigation or the source-wide set, including rows with `linkCurrent:false`, proposals omitted from citations and proposals absent from the set of current compiled candidates. Validate each row against its exact immutable proposal/assessment/source payload and retained investigation union before interpreting its result. Compiler observations from another proposal ID, capture or payload cannot be relabeled as observations of the locked current input.

For the locked current input subkey, choose the greatest first-admission sequence among **settled, structurally valid terminal compile outcomes** across all its assessment revisions. A `compile_blocked` outcome remains unresolved for finish, including its safe compiler codes even when its original assessment row was clear. A blocked outcome with no codes does not become successful; expose unresolved outcome/assessment uncertainty, with no invented repair code. A later settled `compiled` outcome may supersede earlier compile failures in this lineage only when its registration and immutable input bindings are valid and its assessment can be revalidated against the locked current findings, sticky origins, retained applicability and current authority. An older assessment number alone does not disqualify an otherwise identical input; a changed blocker set, stale evidence reference or invalid registration does. That revalidation does not republish a stale current compile pointer or waive finish's independent current-compiled requirement.

A reserved/registered/nonsettled newer attempt is not a terminal replacement: retain the last unresolved terminal outcome and separately report in-flight/unknown work. An obsolete or malformed result cannot supersede anything. When a proposal has advanced to a new input subkey but has no settled result for that input, inspect predecessor revisions newest first until reaching one with valid terminal outcomes, then select that revision's greatest first-admission sequence across its assessments. If it is blocked, keep it as a **carry-forward diagnostic obligation for finish**; a revision change or new clear assessment alone is not a successful repair. If it is a valid historical compiled result with exact registration and clear settlement assessment, earlier failures already superseded by that success do not reappear; this historical success still does not establish that the new current input compiles. Do not offer predecessor codes as exact-current-input `beginRepair` diagnostics: the current input must be compiled to obtain those. A valid terminal outcome for the new current input replaces the predecessor compile outcome; a failure remains blocking, while a valid revalidated success removes the obsolete compiler failure. A different proposal identity cannot supersede the old lineage. This is derived selection over history, not permanent copying of every historical failure into the sticky finding ledger. Finding/capture/authorization blockers remain independently authoritative and never disappear by this compiler supersession rule.

**Verification selection key.** Use `(runId, proposalId, proposalRevision, accountId, subjectHash)` and require byte-for-byte equality of the canonical `subject_bytes` within that key. `subjectHash` is the existing `discoveryVerificationSubject` hash, including the canonical registered candidate, its ordered profiles, complete manifest/snapshot and `snapshotObjectHash`, plus `(runId, accountId)`. Validate these bytes and the linked immutable reservation against the current proposal's exact spec/profile/capture and the specific registered artifact; do not substitute a hash of only the proposal ID, account or artifact. Different profile, artifact, manifest, snapshot, candidate bytes or parent account yields a distinct subject, even when a proposal ID is shared. Assessment revision, requesting task, requestKey and jobId remain exact provenance and are excluded from the supersession key.

For repair, a verification partition is applicable only if the proposal revision is current, its exact candidate subject still matches the locked immutable proposal input/capture, and saved admission plus current coordinator authority permit that parent account and source. Revalidate the associated discovery assessment separately; assessment revision changes alone neither split the verification subject nor clear its diagnostics. A historical registered subject can be examined after its current presentation link was invalidated, but cannot become a current compiled candidate through this selector. Old proposal revisions and distinct verification subjects remain historical, not diagnostics of the current subject; their observations never supersede one another or resolve discovery blockers.

Within each applicable verification subject choose the greatest first-admission sequence with a terminal, validated safe job observation. A completed safe summary supplies its exact failed/unavailable check diagnostic codes; passed checks supply none. A failed job supplies only its existing safe `VERIFICATION_FAILED` diagnostic. A later valid completed summary supersedes an earlier observation **for that same subject**, preserving any failed/unavailable diagnostics in the later summary; a summary with passed checks does not clear another subject's failure. A newer queued/running/interrupted/unknown attempt does not supersede the last terminal observation, supply an invented failure code or establish success. Keep its uncertainty separate. Missing/inconsistent summary/subject bindings fail closed. A summary omitting required check coverage is not an all-passed superseding observation: retain earlier unresolved diagnostics for omitted checks and the existing unavailable-coverage semantics. No hidden report/holdout bytes are consulted by a product tool.

Verification diagnostic selection supplies repair evidence; it does not introduce financial eligibility as a finish prerequisite. Finish still checks every already specified server-owned blocker and known compiler outcome, while keeping protected verification eligibility and the existing nonblocking uncertainty warning separate. If both selected compile and verification observations contain a requested code, prefer compile, then lexical verification subject key if needed. Each selected code retains its actual historical `assessmentRevision` and exact compile-step or verification-request/job reference in `diagnosticRefs`; never rewrite that revision to the current head. If provenance cannot be established, refuse rather than invent a diagnostic or grant.

## beginRepair

The caller is the current coordinator, but the target may be any existing same-run investigation, including source-wide. Require the proposal's **current** identity head equals `expectedProposalRevision`, its server-retained applicability union includes the target investigation, and caller authority permits that subject. A guessed investigation/proposal association is not sufficient.

Resolve every requested code through the diagnostic selector above, restricted to the exact current proposal input and applicable authorized verification subject. Only actual unresolved selected compile/verification codes qualify, with their historical source bindings retained in `diagnosticRefs`. If no eligible diagnostic exists, or any named code lacks that binding, return `REPAIR_DIAGNOSTICS_REQUIRED`. Codes appearing only in model prose, an unrelated blocker row, a superseded result or a predecessor-input carry-forward obligation cannot unlock repair. Do not expose protected report bytes or holdout answers or rewrite model arguments.

Increment `discovery_investigations.repair_count` once, from 0→1 or 1→2, guarded by the current locked value. A third fresh repair returns `REPAIR_LIMIT` and persists the existing exhausted-budget block semantics. The source-wide investigation has the identical limit. This neither consumes nor resets financial verification attempts; verification still independently permits the initial attempt and at most two repairs per run/account, with exact admitted request idempotency.

Bind unfinished, quiescent existing tasks of the target investigation to the new round by setting only `repair_round` and incrementing their normal revision. Quiescent means queued/waiting with no reserved model dispatch or nonterminal tool step. The current coordinator is a narrow exception when repairing its own source investigation: its already returned current dispatch and this exact repair batch may be present; no other active work in that investigation may cross the round transition. Its normal step resolution supplies its one task-revision increment; do not add a second increment for rebinding and break the dispatch/ordinal fence. Reject `DISCOVERY_CONFLICT` if another target task has a reserved call, unresolved returned tool batch, running work or an interrupted unknown outcome. Never relabel the round of in-flight work. Lock and project the full affected task set before incrementing.

Previously succeeded/failed/interrupted tasks remain historical and unchanged; no reset/requeue/resurrection. Newly delegated tasks initialize `repair_round` to the target investigation's current `repair_count`, within the unchanged specialist budget. A repair does not create a task itself. Reusing a queued/waiting task preserves all model attempts and tool rounds; exhausted tasks cannot obtain more calls through rebinding. Existing dispatch/step history remains immutable except already authorized lifecycle columns.

Repair admission does not revise findings/proposals, mark diagnostics resolved, clear run blockers, or declare a previously stale artifact current. Recompute server assessment as required for observed concurrent changes, retaining sticky origins and prior applicability unions; any needed new assessment/current-pointer invalidation commits with the repair. Actual later finding/proposal mutation continues to invalidate compilation/replay/verification links through the existing rules. Repair round alone grants no capability and no exemption from those checks.

## finishRun

Use an explicit finish path in the existing owner executor, not assistant `done`, generic final-step queueing, or a new scheduler. Fresh finish requires coordinator role, a singleton finish batch, runnable run/current authority, and the exact current returned dispatch/step fence. Its own in-progress coordinator task and finish step are the only work exempted from the terminal-work checks below.

Under the run and deterministically ordered investigation/task locks:

1. Every other task must be `succeeded`. All task dependency edges must refer to same-run succeeded predecessors, including the caller's dependencies. Failed/interrupted/waiting/queued tasks are unfinished, not silently discarded. Reject any other pending/running/interrupted tool work or reserved model dispatch. The caller's dispatch must already be returned with accounting recorded; finish does not consume an extra model turn or reset usage.
2. Enumerate **all** opened investigation rows and the run's source-wide set, not just proposal citations or current aliases. Query sticky control007 blocker origins directly, all applicable current findings, capture/authorization diagnostics, current server assessments, **and persisted compile outcomes from `discovery_compile_steps.result` across every proposal in that scope**. Apply the explicit diagnostic lineage/input keys and supersession selector above. A failed compile stored with `linkCurrent:false` blocks even if its persisted current assessment is clear and another proposal is compiled. Unresolved outcomes, predecessor-input carry-forward obligations or missing provenance return `DISCOVERY_ASSESSMENT_UNRESOLVED`; there is no requirement to copy those compiler codes permanently into assessment rows. Recompute finding applicability/assessment using stable source/raw-tuple keys and the retained proposal investigation union. Omitted findingRefs, new proposal IDs, supported revisions, financial reports and consumed requests cannot clear a blocker. Persist newly detected assessment/stale-link effects atomically with an incomplete result where necessary.
3. Prove at least one current proposal head is `compiled` with the exact current proposal/assessment/profile/artifact binding and settled registered compile record. Recompute its assessment under the current run lock and compare the exact current finding heads, blocker set and immutable payload binding; stale compile/registry-only objects do not qualify. An older observedRunRevision caused only by bookkeeping is not alone proof of staleness or currentness: revalidation must establish that its material inputs and assessment have not changed. Record the finish check's observed run revision in the durable step provenance. Any changed assessment invalidates the old current claim; never manufacture a fresh successful compile from the historical registry object.
4. Require no unresolved server-owned blocker anywhere in the enumerated run scope. Preserve existing nonblocking warning semantics, including `VERIFICATION_INTERRUPTED`; do not convert financial verification eligibility into an added completion gate. A current financial report cannot clear discovery assessment. Conversely this completion state does not assert that protected verification has passed or even run.

If incomplete, store the strict incomplete result with safe categories and normal step/task/run accounting. Unfinished work may continue under the existing scheduler; substantive existing blockers retain their blocked state.
