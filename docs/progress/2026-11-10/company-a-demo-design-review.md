## Verdict

The narrow design is feasible and consistent with frozen T0 and existing P1. Release increment A for implementation with the two recovery clarifications below included explicitly in its dispatch. They require no product decision, new migration, scheduler, grant, or accepted-writer change. Do not accept an A implementation that retains the literal exact-set-only lookup or treats fixed-scenario historical-unit validation as optional.

## Required recovery corrections

1. **Locate any association with either frozen event, then enforce the exact pair.** Step 2 currently says query candidates whose event set is exactly the pair, while also promising to reject partial/conflicting associations. An exact-pair-only predicate cannot find a receipt containing one member, or the pair plus additional events. Query bounded overlapping associations (or their delivery/unit association indexes), validate the located receipts through accepted readers, and require exactly one coherent pair-only result. Any partial, extra, multiple, or inconsistent historical association must fail closed. Keep SQL as a locator, not proof. This is a narrow correction to the advertised recovery contract; the existing applier would usually fail closed later, but that is not the promised exact recovery classification.

2. **Require the validated unit and apply the fixed-scenario binding guard during recovery too.** `readSyncReceipt(client, scope, planHash)` validates generic financial history but returns only a `SyncReceipt`: no `asOf`, bundle hash, source account, effective/observed times, or raw fixed amount/invoice relationship. Matching event IDs plus actual activation/artifact does not establish that this is the frozen scenario. A valid earlier receipt for reused scenario IDs at another instant or with different facts must not be reported as this demo's successful retry. For this new mount, require the referenced P1 unit through `readSyncUnit(client, identity, unitHash)`, its receipt/plan identity, fixed evaluation instant and lane, exact pair of validated covered events, and the same fixed facts checked before new application. No legacy no-unit fallback is needed for a mount that only creates P1 units. Do not reimplement historical financial validation: reuse the readers and add only scenario predicates.

Source evidence: `packages/parent/src/sync-store.ts:123` checks canonical plan/receipt, actual A5 activation/artifact/profile, original target snapshots and balances; `:500` validates its unit or legacy history; `:533` returns the receipt alone. `:486` exports `readSyncUnit` with exact committed identity. `apps/worker/src/sync/apply.ts:185` constructs audit including `asOf`, coverage and members. `db/runtime/005_sync_apply.sql:3` persists canonical full plan/receipt, while runtime006 retains units and delivery outcomes. Existing APIs suffice; no request journal is necessary.

## Bounded drain: acceptable, with concrete implementation obligations

The design correctly drains until an empty page, not `complete:true`. `packages/sources/src/change-feed.ts:22` returns up to pageSize events and always returns a validated complete page; its `next` remains `after` when empty. Company A declares both streams with pageSize 100 (`packages/sources/src/company-a.ts:34`).

Choose the finite page cap explicitly in A and count every fetch, including retries/refetches and empty probes. A 1000-event budget needs room for terminal empty probes across both streams; reaching exactly the event budget cannot itself mean drained. If a further nonempty page exceeds the budget, fail without application. Previously captured complete pages may remain durable as specified. Test the boundary, nonempty complete pages, exhaustion, stalled/refetch progress, and both streams. Each attempt is bounded even with concurrent capture.

`createRuntimeCapture.openCommitted` (`apps/worker/src/sync/capture.ts:15`) returns lane/capturePage/readProgress; progress supplies initialized baselines/checkpoints. It does not separately return the manifest's resumeAfter. Use those checkpoints or the verified stored bundle, not an assumed extra API field. `capture-store.ts:347` returns `refetch` for older unsaved page forms; `:355` returns `empty` without checkpoint advancement. Never treat a stale empty fetch as drainage of a newer checkpoint without checking its binding/progress. P1 independently rejects semantic changes, foreign scope, incidents, unsupported history and changed coverage (`apply-types.ts:35` onward). No cross-database source fence is implied.

## Minor notes and proof limits

- Preserve `readSyncReceipt`/`readSyncUnit` storage errors; a later recovery attempt must not convert an unresolved invalid-history error into success. Recovery after pause/revoke is valid immutable history, while new application still requires active current authority.
- Explicitly test a receipt with overlapping-but-not-exact event IDs and a valid receipt/unit with exact IDs but wrong scenario facts/asOf; these distinguish the two corrections from happy-path retry tests.
- Reconstructing a service object proves durable service recovery. Actual process restart/response-loss and worker environment/import evidence belong to the mounted B/C tests and must remain separately labeled.
