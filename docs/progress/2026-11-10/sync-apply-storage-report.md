## Storage and historical reads

- Runtime006 adds common typed origin ownership across both existing economic domains. It rejects missing, ambiguous, and mismatched historical claims before backfill. It checks receipt membership in both directions, scoped bindings, historical snapshot membership, and canonical digests before copying concrete claims. There is no backfill of units, outcomes, or application heads.
- The existing nonempty runtime005 receipt table and its indexes stay in place. Legacy delivery associations remain SELECT-readable. The app role loses INSERT on that table. A legacy exact receipt recovers only after its canonical plan, committed activation, artifact/profile, receipt indexes, before/after snapshots, ordered record IDs, and original delivery/economic associations validate.
- Scoped foreign keys bind units and heads to the exact committed import and lane, including imports sharing a lane whose first activator differs. Nonempty units reference runtime005 receipts and advance one target version. An all-replay unit requires no receipt and retains its exact snapshot. Unit and outcome canonical bytes and digest are bound to the indexed scalars. Event outcomes link exact inbox and source-position membership, an original scoped financial origin, and the first acknowledging unit. The SQL trigger checks the canonical event content hash, original receipt bytes, and exact membership in that unit.
- An app-role head insert starts at the checkpoint's exact approved baseline with a null last-unit hash. Only `applied_through` and `last_unit_hash` are mutable. A subsequent update must use the same scoped financial unit beginning at the old frontier and ending at the proposed frontier, at or below capture. Semantic heads stay at their approved baseline. The four histories have immutable triggers where applicable and no app DELETE/TRUNCATE privileges.
- `readSyncCommit(client, identity, plan)`, `readSyncUnit(client, identity, unitHash)`, and `readFinancialOrigins(client, scope, records)` validate exact persisted facts with SELECTs. They do not consult source availability, today's capture cursor, today's reviewer configuration, or current authority epoch. Exact plan recovery returns the committed receipt epoch. Parent integrity errors use the existing `SYNC_STORE_INVALID` code. Worker mapping and new-write epoch checks belong to Task 3.
- The inherited `readSyncReceipt(client, scope, planHash)` validates persisted history for the old consumer. Task 3 should switch ongoing recovery to `readSyncCommit`. The old `persistSyncBatch` and worker apply call site remain untouched in this candidate. The old writer's legacy delivery INSERT is intentionally no longer permitted with 006 and must be replaced in Task 3. Unmatched legacy history blocks new work in Task 2's coverage check.

## Shared interface for Tasks 2 and 3

Import through the existing `@eapr/parent/sync-store` subpath. It exports `CoverageCutSchema`, `SyncUnitAuditSchema`, `SyncEventOutcomeSchema`, `SyncEventRefSchema`, `ReceiptOriginSchema`, `UnitMemberSchema`, their types, `hashSyncUnit`, and `syncEventRef`.

- The cut has `identity, lane, manifest, capture, manifestDigest, captureDigest, initialActivationId, initializedAt`. The exact `baseline` fields are `importKey, receiptId, activationDigest, bundleDigest, approvedSnapshotHash, approvedTargetVersion`.
- `checkpoints` rows are `{streamId, transport, baselineCursor, captureCursor, capturedPages, lastCapturedAt}`. `capturedPages` is a safe nonnegative decimal string. `applicationHeads` rows are `{streamId, baselineCursor, appliedThrough, lastUnitHash}`. Both arrays sort by stream ID. Absence is represented by omitting the corresponding stream from the heads array, while an existing baseline head is represented by an explicit row with a null last-unit hash.
- `positions` rows are `{sourceRef, streamId, sequence, eventId}`. `inbox` adds `manifestHash, afterCursor`. `deliveries` rows are `{event, digest}` and preserve the exact raw canonical event. Position/inbox/delivery arrays are in sequence order for the accepted single financial stream. `pages` rows are `{sourceRef, manifestHash, streamId, afterCursor, nextCursor, eventCount, digest, capturedAt}` in ascending numeric cursor order. Task 2 must validate the actual raw page, digest, and indexes before projecting that compact row. The stored audit reconstructs complete canonical pages from ordered members and checks their digests.
- `historyUnits` rows are `{unitHash, auditDigest, streamId, fromCursor, throughCursor, beforeTargetVersion, beforeSnapshotHash, afterTargetVersion, afterSnapshotHash, receiptId}`, ordered by starting frontier. `historyOutcomes` rows are `{event, recordId, unitHash, disposition, digest}`, ordered by position. `historyOrigins` rows are `{recordId, initialImportKey, initialReceiptId, syncReceiptId, receiptDigest}`, ordered by distinct record ID. Prior unit digests/endpoints are references without nested audits. Task 2 validates prior immutable units separately by exact key.
- `guards` has booleans `overflow, extraLane, undeclaredStream, nonselectedPostBaseline, outOfCut, incident, unmatchedLegacyHistory`. Accepted persisted audits require all false. All per-position collections are bounded to 1,000. Detect SQL overflow before projecting a rejected cut into this representation.
- The unit key is `{identity,lane,streamId,expectedEpoch,expectedTargetVersion,beforeSnapshotHash,asOf,coverageHash,planHash}`. Compute with `hashSyncUnit` using those exact fields. The audit adds `coverage,unitHash,fromCursor,throughCursor,afterTargetVersion,afterSnapshotHash,receiptId,semanticObservation,committedAt,members`. `planHash` and `receiptId` are both null for all-replay. There is no separate persisted prepared event array or plan copy. An event outcome is `{identity,lane,unitHash,...member}`. A member's original receipt is typed initial or sync. A mixed receipt's ordered event list includes replay acknowledgments and its ordered target IDs contain only newly written records.
- New SQL row names match the brief. Unit payload fields are `audit,audit_digest`; event outcome payload fields are `canonical,digest`. Initialization and advancement of a new application head are separate statements in the same writer transaction. An existing baseline head is distinguishable from an absent row.
