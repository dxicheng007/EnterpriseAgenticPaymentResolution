## Blocking findings

1. **[P1] Read the dedicated authority endpoint before enabling commands.** `apps/web/src/features/connections/OperationsPage.tsx:70-77,127-142` and `packages/client/src/parent.ts:74-98`. The only read is the overview, and its status/epoch directly enable and construct mutations. Actual `apps/worker/src/connections.ts` explicitly falls back to active/epoch1 when an initial import exists without a head. It also depends on mutable registered scopes independently of the authority route. Thus a valid overview plus unavailable/forbidden authority read still presents actionable controls; conversely unavailable overview hides otherwise accessible committed authority. The mounted `/api/connections/:accountId/authority` endpoint already exists and returns `CurrentAuthorityV1` with exact committed identity. Consume it independently, show its failures separately, and do not let overview/initial receipt enable actions. Success/no-op/replay must refresh both authority and overview; currently only overview refreshes. This is explicitly required by `docs/progress/2026-11-10/authority-operations-ingress-design.md`, Experience-facing contract.

2. **[P1] Preserve the unresolved command rather than rebuilding it from refreshed state.** `OperationsPage.tsx:75-88,106-118,164`. A map from action+epoch to key is not a pending account/action/body. Repro from actual service semantics: pause at epoch1 commits but response is lost; follow the UI instruction to refresh; overview now says paused epoch2 and removes Pause, leaving no way to retry the original pause. If a peer resumes to epoch3 before refresh, the next Pause produces a new key/body at epoch3 rather than recovering the epoch1 result. Switching away and back also destroys the map. The service intentionally replays an exact original command before checking current epoch, so the API supports recovery; this UI loses it. Retain a pending immutable request and provide explicit retry under fresh admission independently of refreshed available actions. Avoid presenting network/503 outcome as unchanged: authority transitions write command audit, not the financial receipts shown here, so “unchanged unless a receipt shows otherwise” is misleading.

3. **[P1] Handle 409 as refresh plus a new deliberate action.** `OperationsPage.tsx:91-95,118`. All failures only set a generic error. If another reviewer pauses/revokes after the page loaded, Pause returns AUTHORITY_STALE (409), but the page retains the old authority and buttons and sends the same stale request again unless manually refreshed. For conflict at an occupied key, refreshing to the same epoch retains that key forever because the map has no retirement/new-action operation. Distinguish stale/conflict terminal rejection from uncertain delivery; refresh authority and overview on 409, retire the rejected attempt, and require a new deliberate action/key against newly read authority. No automatic reauthorization or mutation retry is requested.

4. **[P2] Add same-identity nondecreasing authority state handling and its regression.** `OperationsPage.tsx:127-142`. Every successful read blindly replaces state; there is neither committed identity comparison nor an epoch floor. Abort cleanup prevents an obsolete effect callback after its cleanup, but does not implement the contract's identity/epoch rule or retain the epoch established by a successful command while refreshed reads are pending. A delayed lower-epoch snapshot must not replace an already observed higher-epoch state; an old replay result is historical and cannot establish current status. Implement this with the dedicated authority read, and exercise delayed/out-of-order results including old pause replay after revoke. This is a source-confirmed missing requirement; no executed race reproduction is claimed.
