## Bounded deliverable and actual producer surface

Implement request/read consumers for exactly one already-registered compiled profile whose account is already trusted by saved and current grants. Naming a proposed account never grants capability. Keep repair, finish, generated-scope policy, model/provider configuration, protected fixtures and financial rules outside this work.

Consume `@eapr/evaluator/discovery-verification`, not legacy `jobs.enqueue` or reviewer `enqueue`. Its actual surface is:

- `createDiscoveryVerification(options)`, where options extend financial jobs dependencies with `gate: DiscoveryVerificationOwnerGate` and `resolveTaskId({requestKey,runId,accountId})`.
- `enqueueDiscoveryVerification({requestKey,candidate,task:{runId,accountId}}): Promise<VerificationJob>`.
- `readByRequestKey(theSameInput)`: absent or existing safe job plus `executionUncertain`.
- `get(jobId)`: trusted metadata only, **no authorization**; never expose it directly as readVerification.
- `drain()`: tracked in-process executions only; it is not a recovery protocol.
- `discoveryVerificationSubject(candidate,task)` plus exported identity/binding/gate/outcome types and fixed `DiscoveryVerificationFailure` codes.

`resolveTaskId` performs durable association lookup, never accepts a model-supplied task. It is a resolver, not an authorization substitute: all three gate methods reauthenticate. The producer's historical lookup still requires the original full CandidateRegistration. Consumer must reconstruct it from immutable mapping subject bytes and validate canonical bytes/hash/schema and historical proposal/compile association before invoking producer. Never reconstruct from today's proposal head or require a fresh registry filesystem lookup merely to read an existing completed job. Producer validates saved financial reservation association internally; do not import its private readers into Discovery.

Factory dependency injection must avoid circular acquisition: pass an optional server factory into service/supervisor, then instantiate the producer inside each acquired supervisor using that owner's gate and resolver. A replacement gets a fresh producer and local execution map. Do not share a producer closed over a discarded owner, and do not reuse its process-local running map to prove a replacement owns execution. Old positively claimed execution may complete its original financial job, but cannot publish through the new owner automatically.

## Actual owner transaction integration

`supervisor.ts` owns a dedicated `pg` client, advisory lock `[1161908306,4]`, generation and `serial` promise chain. Existing `transact<T>` returns `T | undefined`; undefined conflates invalid owner, rollback and lost COMMIT acknowledgement. It cannot implement the Gate P port by treating a callback return as committed.

Introduce an internal outcome-aware transaction runner on the **same client and same serial queue**. Keep the current `transact` facade for source/compile/replay callers, preserving their behavior, while owner-gate operations consume explicit outcomes. Do not nest `transact`, acquire a pool connection from a gate callback, or wrap an ordinary pool transaction in a synthetic owner check.

Track whether COMMIT was attempted and acknowledged. Return `committed(value)` only after positive COMMIT acknowledgement and valid owner checks. If owner loss occurs before COMMIT and rollback/no commit is established, return `owner_lost/not_committed`. Once COMMIT was sent without confirmed outcome, return `owner_lost/unknown`; a subsequent successful ROLLBACK does not prove that prior COMMIT failed. Loss detected after acknowledgement but before publishing success may conservatively return unknown. Never return the callback value on any lost-owner branch. Preserve SQL errors, including `23505`, through the runner so producer's fresh authorized lookup on unique contention remains reachable; gate denials are fixed safe codes, not arbitrary exceptions or success-shaped values.

Callbacks are trusted SQL-only producer closures, invoked exactly once per gate invocation on that owner client; no external capture/registry/probe/build/child I/O inside them. Validate ownership and applicable grants immediately before commit as well as before callback. Existing run/task locks serialize pause and other durable mutations. Order locks as owner queue → run → investigation/task (existing `lockTask`) → step/dispatch → proposal/current assessment when required → mapping → budget/job/reservation → activity last. Never hold an activity counter while acquiring another run. A failed invariant rolls back the complete gate operation. Any durable revoked-authority observation needed after rollback is a separately owner-fenced safe transaction, not a partial financial reservation commit.

| Gate | Required authority and associations | Explicitly not required |
| --- | --- | --- |
| `lookup` | Current owner; run reviewer/source/company; saved run covers saved task and current grants cover saved task; original account is trusted; exact step/dispatch/run/task identity and accepted-call integrity; immutable mapping subject/job/request/assessment associations | Current proposal head, current task revision/attempt, old generation equaling current generation, runnable run, nonterminal tool step |
| `admit` | All current execution fences; connector role; runnable run; first unresolved valid step; exact dispatch and accepted batch; current task revision/attempt/generation; complete batch preflight; exact compiled one-profile subject, clear current assessment and capture; saved/current trusted account; repeated mapping check | No permission inferred from absent lookup, candidate argument, UUID, or model TaskContext |
| `recoverQueued` | Current replacement owner and source/account authority; original immutable mapping and historical step/dispatch/proposal/assessment association; queued-only producer callback | Old task revision/attempt/generation still current, original proposal still head, runnable/unpaused run, new budget, current-link publication |

Current `loadStep` validates accepted dispatch hashes/tool IDs for construction batches, but also rejects stale task attempt/status/revision. Extend its construction classification for new verification tools; do **not** weaken those checks globally. Add a distinct historical association loader for lookup/recovery, validating the accepted ModelResult, `createToolStepId(dispatchId,nativeId)`, ordinal/name/arguments, mapping's original dispatch, bounded revisions/generation and exact saved proposal/assessment. A terminal or interrupted step remains a valid historical association. A raw request key, job ID, JSON TaskContext projection, or FK alone is insufficient.

Use `coversGrant(run.grants,task.grants)` and `coversGrant(resolveAuthority(run.reviewer_id,run.binding),task.grants)` consistently; additionally require the original profile account in those trusted allowedAccountIds and source/account applicability under the pinned capture. Preserve source evidence and agreement association checks. If authority loss is observed for abandoned verification work, persist a sticky forbidden lifecycle observation using existing task/run mechanisms; restoration or resume must not erase it or turn that abandoned step into success. A discovery diagnostic never changes the financial job state.

## Admission, complete-batch validation and settlement

1. Parse all remaining calls and validate accepted batch integrity before any successful effect. Add both tools to the strict parser/result replay paths and unavailable/forbidden handling. Preserve delegation capacity, finding/proposal projected assessment checks, capture checks and the complete 65,536-byte result bound. A later invalid verification call must prevent an earlier source read, finding publication, compilation, replay or verification admission in the batch from succeeding.
2. For each proposed new request, resolve the exact current compiled proposal/assessment and existing settled compile registration; require exactly one profile and trusted account, exact artifact/spec/profile/capture hashes, matching registered CandidateRegistration. `loadReplaySubject`/`loadCompileSubject` provide current SQL checks but do not alone authenticate full registered bytes. Load external registry/capture facts outside the owner transaction, compare immutable identities inside it. Never compile implicitly, split multiple profiles, or infer registration from a proposal's artifact string.
3. Preflight the whole batch before invoking producer preparation, then repeat relevant preflight inside `admit` after preparation. Project preceding finding/proposal changes when checking later verification subjects; an invalidated or not-yet-compiled subject cannot be admitted on an optimistic same-batch future result. Include all prospective verification admissions in the run/account budget projection; the producer's max-three SQL reservation remains authoritative against races. Safe rejection/terminal bookkeeping is permitted, but no successful earlier batch effect may escape a failing preflight.
4. Call enqueue outside any owner transaction with server-selected step ID and registered candidate. Historical lookup occurs first. For absence, preparation may perform protected probe outside the transaction, then `admit` repeats current authority/capture/subject/assessment/batch checks. Derive `AdmissionBinding` from locked records using `discoveryVerificationSubject` on the authoritative registered candidate; supplied expected hash is only an equality assertion. Callback inserts budget/job/reservation/009 mapping; gate claims the Discovery step on the same transaction and publishes only allowlisted activity. Mapping is the durable claim/reference; do not add a redundant mutable current-job pointer.
5. Producer subsequently invokes `recoverQueued`; only committed + claimed permits external saved-input execution. Returning a running VerificationJob is an admission/execution observation, never financial eligibility. Enqueue return does not wait for a report. Request tool may settle to a safe job reference after a fresh current settlement check; later readVerification obtains the actual job state. Report completion itself does not update proposal readiness.
6. Before current tool success/transcript publication, reload through the actual owner and recheck generation, dispatch, step/task revision, saved/current grants, pinned capture, current proposal revision, assessment revision and exact compiled subject. Recheck authority just before commit. Owner loss, pause, changed finding/assessment, task revision or proposal prevents current success; immutable original mapping/report remains historical. Do not retarget, delete, or rewrite the mapping to fit the new head. Financial completion can occur independently after admission without granting current Discovery success.

No new proposal eligibility state is introduced: ProposalResult's compiled state and assessments retain existing semantics. Financial eligibility comes only from the attested job summary. Bootstrap readiness and reviewer approval remain separate.

## Recovery that actually runs while paused or stale

The current service tick selects only queued/running runs and active task attempts, and `reconcile()` handles only source reads/compile/replay/compare. Merely adding verification to the current recoverable names does not meet the accepted recovery design.

Add a bounded, owner-fenced admitted-verification recovery pass driven by 009 associations and financial job state, independent of fresh model scheduling and current task attempt. Run it on owner acquisition and subsequent service ticks, including paused runs and stale task/proposal revisions. It may inspect historical mappings and claim existing queued work; it must never synthesize a tool call, reserve a new job, call the model or bypass current authorization. Pending discovery steps without a mapping remain subject to ordinary runnable admission. Serialize recovery per original request and use the owner's transaction queue; duplicate scans are harmless because producer claims queued only. Do not let `pendingTasks`/`pendingSteps` for a newer task attempt suppress recovery of an older immutable request.

| Durable state at interruption | Recovery behavior |
| --- | --- |
| Admission rolled back, mapping absent | No job/attempt/claim survives. Only fully revalidated current admission can start work; paused runs cannot admit. |
| Admission COMMIT unknown | Discard temporary job ID and prepared authority. Fresh authorized lookup; if absent, normal admission rules; if present, recover original mapping. |
| Existing queued job | Reconstruct original candidate, call enqueue with original key/subject; recoverQueued can claim while paused or stale. No probe, fixture reselection, build refresh or extra attempt. |
| Queued→running COMMIT unknown | Never launch or fail. Replacement reads durable state; queued may be claimed, running may only be observed. |
| Running with no positive local claimant | Return running plus fixed `VERIFICATION_INTERRUPTED` lifecycle observation. Never relaunch, reset, time out into failed, or create replacement job. |
| Completed/failed | Read same original job/report with no new budget or launch. Current settlement still has its own fences. |

`readByRequestKey.executionUncertain` is usable after original-subject authorization. Project a fixed message: “Verification execution outcome is uncertain; automatic relaunch is unavailable.” Persist interruption history through existing safe activity and associate only already-authorized job/step identities. Expose the current observation in tool output and run diagnostics without using `markBlocker` to invent a new permanent eligibility blocker. Run diagnostic projection may derive uncertainty from durable running associations and the recorded interruption observation; do not infer uncertainty solely from absence of a Promise in repository code. When a confirmed completion is later read, show completed state and remove the current uncertainty projection while preserving lifecycle activity history. Sticky **authority revocation** remains separate from this nonterminal uncertainty observation.

## Safe schema proposal and scoped state reads

Publish together with consumer implementation and joint review, using strict Zod plus matching descriptor schemas. Proposed exact model inputs:

- `requestVerification`: `{ proposalId: Id, revision: Version }`.
- `readVerification`: `{ proposalId: Id, revision: Version, jobId: Id }`.

Neither accepts requestKey, accountId, candidate bytes, fixture/build selection, proof, grants, reviewer identity or task context. Read resolves 009 by job and exact proposal revision **within the current authorized run**, then obtains the original request/subject internally. A read tool's own step is separate from the original request step. Current read-call settlement is fenced normally; the target association may be historical.

Proposed successes for both: `{ ok:true, proposalId, revision, job: VerificationJob, observation?: { code:'VERIFICATION_INTERRUPTED', message:<fixed literal> } }`, bounded to 65,536 UTF-8 bytes. `ok:true` means an authorized observation, not passed verification; failed/running jobs retain their real job state. Use fixed allowlisted failure codes for invalid/forbidden/conflict/unavailable/paused/scope-required/owner-lost/result-limit outcomes; add the missing codes to the proper tool failure schema rather than accepting arbitrary strings. Keep owner commit certainty internal. Do not expose producer binding/subject bytes, request hash inputs, financial reservation, protected root/pin/fixture/truth, launcher stderr or raw errors. Preserve the existing VerificationJob wire unchanged.

`repository.ts:project` currently hardcodes `verificationJobs: []`; `authorizeRun` currently checks reviewer/source, not task account coverage. Replace the placeholder with a same-snapshot association query joining 009 to its original step, dispatch, proposal assessment and job/reservation identity. Validate original subject and current saved/task/source/account authority before projecting each association. A run_id-only join or arbitrary get(jobId) is insufficient. Preserve existing schema `{proposalId,proposalRevision,jobId}` and canonical ordering/deduplication; include authorized historical associations, never relabel them as current. Current `proposals` remain separately projected. Foreign-run/account jobs and legacy reviewer jobs with no 009 mapping must not appear. Ensure pause/resume response projections and idempotent saved response handling cannot return newly unauthorized verification associations; reauthorize those saved references before replay or rebuild the safe projection without changing the saved mutation's semantics.

No new HTTP route or browser detail flow is required. Any activity schema additions must use explicit fixed safe fields, bounded messages and existing redaction rules, with contracts owner review; never widen a generic payload to fit private data.

## Gate order, composition and escalation

Implement and test the consumers with explicit test injection first. Keep production tool advertisement/mounting disabled until root records Gate J machine evidence and independent exact-candidate acceptance. Afterwards root may inject a factory built from the existing registry, financial capture reader, protected launcher, operator-selected construction fixture and fixed build hash, following current protected-root validation in financial composition. Factory receives the actual owner gate/resolver; it does not receive authority to choose arbitrary fixtures or approve a customer. Discovery receives a narrow request/read capability; no model key, raw proof, protected file reader or fixture selector is placed in tools/arguments/results. Default composition has no model client; Gate J does not configure one. Runtime remains model-free and receives no Discovery dependency.

No confirmed producer defect was identified by this design inspection. Concrete integration hazards are explicit: original CandidateRegistration is mandatory even for historical reads; raw get is unauthenticated; safe enqueue return has no uncertainty field (follow with scoped read); unique-conflict recovery depends on preserving SQL state; producer has no completion callback/current-settlement authority; running ownership is instance-local. The plan above accommodates these actual contracts. If original subject reconstruction or a SQL-only owner callback cannot be implemented without fresh protected I/O or altered producer semantics, stop that dependent path and report the precise signature/invariant mismatch to Platform/root. Do not paper it over with current-head substitution, generic pool reservation, permissive gates, guessed commit success or public internal bytes.
