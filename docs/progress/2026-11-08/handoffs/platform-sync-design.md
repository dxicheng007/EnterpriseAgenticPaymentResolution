# Platform deterministic ongoing sync: staged engineering design

**Status:** Design for independent review; no implementation, migration reservation, machine pass, or acceptance claim. Researched against `7a90f1617b70171495dc90adc206cbe873fe09ee`. Evaluator work in progress is unrelated and was not edited.

**Goal:** Capture new source input durably and apply it only under the exact customer's standing authority, preserving original approval history and economic uniqueness.

**Architecture:** Keep source storage in control and parent/inbox/authority in runtime. Extend the existing worker app; do not create a runtime workspace. Deliver the capture/storage contract first, then independently review application and connection-control contracts before their implementation.

**Stack:** Existing Node 24, strict TypeScript, Zod, Fastify, PostgreSQL 18/pg and Vitest. No new dependency, model client, SDK, key, evaluator import or control database credential in worker.

### Capture identity and cursor domains

Use a capture lane `(sourceRef, manifestHash)`, initialized from an existing validated stored activation bundle. This is a technical choice: one immutable baseline per lane makes activation-window catch-up and different customer baseline manifests explicit. Global delivery/economic identity still crosses all lanes. Customers sharing a baseline share capture; an account with a different baseline gets its own lane. Never initialize an older activation from another lane's latest cursor.

A lane pins the exact artifact capture stream definitions and manifest member vector. If two artifacts declare incompatible stream definitions for the same lane, fail closed and report a configuration conflict; do not merge definitions. Baseline event watermarks come from `manifest.streams[].resumeAfter`; CSV batch watermark comes separately from manifest files for that stream. `b-files` event sequence and CSV batch sequence are different domains. Require a contiguous verified baseline batch list and its bound originals before initializing the batch checkpoint. Do not substitute number of files for a checked final sequence.

Delivery identity remains `(sourceRef, event.id)` with byte-equivalent canonical event and hash, including original observedAt (F1). Position identity is `(sourceRef, streamId, sequence)`; pin it globally across lanes, including known baseline events. Same delivery at a different position, different delivery at an occupied position, or changed bytes at the same delivery is conflict. Economic identity remains `(sourceRef, sellerEntityId, kind, recordId)`, excluding account alias, event/version and artifact/profile versions.

### Proposed strict schemas and ports

All objects strict, dangerous keys rejected, IDs/cursors/hashes use existing contracts and safe-integer checks. These names are new and additive; existing ChangePage and financial envelopes are unchanged.

- `CaptureLaneV1 = {schemaVersion:'1', sourceRef:Id, manifestHash:Hash}`.
- `CapturePageInputV1 = {lane:CaptureLaneV1, page:ChangePage}` for API/semantic streams. Caller cannot choose a URL, schema, baseline, account grant or source credentials. Bound stream must be transport api/semantic.
- `CsvBatchDescriptorV1 = {sourceRef, streamId, batchId:Id, sequence:Version, fileId:Id, documentId:Id, documentVersion:Version, contentHash:Hash, byteLength:Version, firstEventSequence:Version, lastEventSequence:Version, eventCount:Version}`. Require nonempty bytes and at least one event, with `lastEventSequence = firstEventSequence + eventCount - 1` using checked arithmetic. Empty CSV batches are rejected with `SOURCE_CONTENT_INVALID`, matching the current `company-b.ts` parser. Empty-batch support is deferred to a separately reviewed source-owner contract covering parser, upload, transport, replay and checkpoint tests; this delivery must not broaden source acceptance.
- `CsvBatchReadV1 = {descriptor:CsvBatchDescriptorV1, events:RawSourceEvent[]}` is the internal result after exact original bytes/hash and fixed envelope parsing. Event count/range, stream/source, unique IDs and hashes must agree. Source service returns the bytes through a fixed capability endpoint so worker can independently verify/decode; a JSON list without original bytes does not establish CSV byte identity.
- `BatchListingV1 = {sourceRef, streamId, afterBatch:Cursor, descriptors:CsvBatchDescriptorV1[], observedThroughBatch:Cursor, missingSequences:Version[]}`. Ordered bounded listing; missing sequences are evidence of advertised absent batches, not inferred from elapsed time. This is a new producer contract, not available today. Pagination must not conceal a gap within the advertised range.
- `CaptureResultV1 = {captured:NonnegativeInteger, cursor:Cursor, replayed:boolean}`. Existing internal `capturePage(page):Promise<{captured,cursor}>` vocabulary is implemented by a lane-bound service closure; no untrusted caller invents lane initialization.
- `captureCsvBatch(lane, batch):Promise<{captured:number, eventCursor:Cursor, batchCursor:Cursor, replayed:boolean}>` requires the next batch sequence and the next contiguous event range. It stores all members and bytes binding before moving either cursor.
- `readCaptureProgress(lane):Promise<CaptureProgressV1>` reports each stream's event cursor, separate CSV batch cursor, observed high water if known, pending gaps and last safe diagnostic. A transport error is lag/unavailability; it is not a successful empty feed.

Private source endpoints proposed: `GET /internal/sources/:sourceRef/streams/:streamId/changes?after=<Cursor>`, `GET .../batches?afterBatch=<Cursor>`, and `GET .../batches/:batchId/content`. Source/stream/batch are validated logical IDs. Reuse installed source-read capability and explicit source allowlist; worker never connects to source/control SQL. Fixed loopback origin, no redirect, 2-second timeout as existing semantics client, streamed hard byte bound (10 MiB CSV as F4; bounded JSON envelope separately), strict UTF-8, JSON/CSV parsing, expected media type, no cookies or caller-supplied headers. Check complete page size against pinned CaptureStream.pageSize (1..1000). Transport credentials stay outside artifacts and UI.

**CSV producer gate:** Current source upload rejects out-of-order batches before publishing them. Therefore the proposed listing must not fabricate missing batch visibility from `source_events`. A staged source producer must supply an immutable advertised batch catalog that can represent an offered later batch and its absent predecessor, without weakening accepted upload/capture semantics. Reserve that producer and its persistence only after source-owner review; no control migration number is assumed. Until delivered, API/semantic capture can proceed, but full Company B gap acceptance is unavailable. Existing sequential complete batches may be transported with explicit limitation.

### Additive runtime catalog proposal

Use canonical text plus digest for immutable domain objects, following runtime002 (including its JSONB validation-projection precautions). Enforce safe integer bounds, scoped FKs, digest/binding checks on read, immutable history triggers and minimum app-role grants. No app-role UPDATE/DELETE of source or receipt history.

| Proposed relation | Key, durable content and mutability |
| --- | --- |
| `runtime_capture_lanes` | PK `(source_ref, manifest_hash)`; exact baseline manifest/capture-definition canonical bytes and digest; append-only. No lane from an unapproved source. |
| `runtime_capture_checkpoints` | PK lane + stream; event cursor, optional CSV batch cursor, revision; update only under row lock/CAS; no account locks. |
| `runtime_source_positions` | PK `(source_ref,stream_id,sequence)`, unique `(source_ref,event_id)`; FK to existing `runtime_deliveries`; immutable. Seed baseline positions from verified bundle before post-baseline capture. |
| `runtime_capture_pages` | PK lane + stream + `after`; exact complete page canonical/digest, next cursor, persisted time. Empty-at-head responses need not be stored as permanent pages, because the next poll at that cursor may contain new events. |
| `runtime_capture_batches` | PK `(source_ref,stream_id,batch_id)`, unique `(source_ref,stream_id,batch_sequence)`; exact descriptor and original-byte hash, immutable. Lane membership separate if reused. |
| `runtime_inbox` | PK lane + `(source_ref,event_id)`; FK delivery/position; immutable capture membership. Raw identity is retained, never assigned an invented approved scope. |
| `runtime_capture_incidents` | Immutable bounded conflict/gap/error observations; original conflicting bytes may be retained privately by digest, never replace first accepted event. Current incident projection can be mutable separately. |

A later catalog phase adds application heads/outcomes/receipts; capture does not preemptively create fake applied outcomes. Baseline imported events continue to use their initial receipt; baseline coverage is separately labeled and never called newly captured/applied work.

### Complete-page transaction

1. Read lane/checkpoint and fetch outside a runtime transaction. Validate registered stream, after/next arithmetic, complete=true, size, source/stream, hashes, unique IDs and required envelope. Source schema mismatch is a contained interpretation failure, not permission to fabricate mapped data. If raw bytes cannot form a valid ChangePage, retain an incident/opaque blob separately and leave the cursor unchanged.
2. Begin `withTransaction`. Lock only the lane's stream checkpoint and recheck expected cursor. A stale cursor does not bypass identity validation: before any benign discard/refetch, proceed to step 3 and compare every response delivery and position with its existing accepted binding, including the winning concurrent page. Exact canonical content includes observedAt; a recomputed valid hash does not make changed delivery bytes a replay.
3. Lock delivery identity keys using the same `parent-delivery` convention as A5, in existing helper ordering. Compare existing global deliveries/positions, including bootstrap history and overlapping positions from concurrent capture. On any conflict persist a safe incident in a separate successful transaction after rollback; no page/checkpoint writes from this attempt survive. Only after these checks, an exact stored page replay returns existing progress. A stale page with matching accepted overlaps but different boundaries (for example, a longer response after ordinary feed growth) is benign: discard it and refetch from the current checkpoint without advancing that checkpoint or inserting its suffix. Never splice a suffix from a stale page implicitly. Continue to step 4 only when the expected cursor still matches.
4. Insert missing immutable deliveries/positions, page/batch and lane inbox membership. Advance checkpoint with exact prior-cursor CAS only after all events are stored. For CSV store entire original binding and all batch members before batch cursor advancement; never advance batch sequence on a partial event page. A batch can contain more than one application cycle, but transport/file size bounds still apply.
5. Publish allowlisted `source.captured` activity last in the same transaction. Commit then emit. Crash before commit leaves old checkpoint; crash after commit replay is identical and adds no records.

The capture lock path never acquires authority, parent target or application-progress locks. Application must never acquire capture checkpoint locks. Sharing delivery advisory locks is safe only if both paths acquire their delivery/economic key set once in helper order and never later reach backward to a checkpoint.

## 2. Application design: next contract gate, not phase-one implementation

### Proposed modules and data

`apps/worker/src/sync/{run-cycle,dependencies,apply,connection-store,progress,reads,status}.ts`; `packages/parent/src/sync-store.ts`; tests `tests/integration/{sync-apply,sync-dependencies,sync-status,v5-sync,v6-sync-recovery}.test.ts` and `apps/worker/test/sync-dependencies.test.ts`. Integrator owns parent export map and any narrowly required persistence refactor. Compiler/finance changes require their owner; do not duplicate or relax money validation in worker.

Proposed additive tables: current connection head keyed by account with original activation FK, status and epoch; immutable status command log; per-account/lane/stream application checkpoint; immutable attempt/outcome history plus current pending/terminal pointer; dependency edges; immutable ongoing receipt/plan/lineage; ongoing delivery and economic receipt associations. Existing runtime002 outcome tables stay untouched. Union initial and ongoing associations for replay lookup. `parent_financial_records` remains the single global economic uniqueness constraint, so adding ongoing associations does not create a second uniqueness domain.

Each ongoing receipt stores the existing SyncReceipt shape, canonical plan, explicit asOf, before/after target versions and hashes, profile hash and lineage as companion audit fields. Link every inserted record and acknowledged delivery to an initial or ongoing receipt with actual enforced FKs (separate nullable reference columns plus exactly-one check is preferable to an unenforced polymorphic receipt ID). Financial replay under a new event ID points at the original receipt. Mixed groups preserve original economics and associate acknowledged deliveries with the new nonempty group receipt as required by F5. No empty monetary receipt is invented.

### Outcome and progress vocabulary

Proposed current outcomes: `pending_dependency`, `pending_authority`, `quarantined`, `applied`, `replayed`, `semantic_observed`. Pending/quarantine carry code, source IDs and dependency identities; applied/replayed require receipt references. Semantic observed is nonfinancial metadata coverage only; changed revisions still establish a blocker. Unknown customer with known company/seller remains source-level unassigned work; missing/ambiguous seller and unscoped governing semantics block source financial application (F1). Do not use an arbitrary skip/resolved API to close monetary gaps.

Per-stream global completion cannot cross unresolved input. Per-account cursor may traverse an input proven outside that account's exact approved identity without claiming that input was globally applied; label it scope-excluded coverage and preserve the source-level hold. A known independent account can progress while another account has a gap. All counts must distinguish source-wide unresolved coverage from selected-account work and baseline coverage.

Maintain highest contiguous terminal position per scope/stream, plus bounded gap summaries and paginated detail. Applied events after a gap do not advance that frontier. Semantic streams and CSV batch progress are separate vector members. Never aggregate vectors into a single timestamp. Capture may advance during dependency holds. Quarantine is not successful resolution, and a connected source with gaps is not fully reconciled.

### Dependency groups and bounded scheduling

Choose cycle asOf once outside pure computation and pin it in every plan/attempt. A cycle selects at most 1,000 source events total, including replay candidates and prerequisites, and never splits an atomic customer dependency group merely to fit. Stable ordering: source stream ID, numeric sequence, event ID; accounts rotate through a persisted scheduling position to avoid starvation. No wall clock in `planBatch`.

For the earliest unresolved customer group, inspect mapping-declared invoice/funding/reversal references and search already captured events across **all** streams for exact same-source/seller/account prerequisite identities. Reuse planner mapping/validation semantics through an explicitly reviewed shared helper if necessary; do not infer dependencies by fuzzy names or assume `Hold.dependencies` alone proves the type of every relation. Build a bounded closure, topologically order, and run `planBatch` against locked target facts. Include later prerequisite invoice events even when an earlier allocation is held. Later unrelated or dependent monetary work for the held customer must not jump ahead; independent customers remain schedulable. Capturing prerequisite events never waits on application.

Technical retry proposal: three distinct persisted dependency examinations before quarantine, with examinations triggered by changed capture vector or bounded scheduled retry, not tight-loop polling. At quarantine, retain dependency indexes; arrival of an exact prerequisite may trigger deterministic revalidation, but no operator button overrides money checks. Cycles, contradictory prerequisite identities and closure exceeding 1,000 remain explicit exceptions. Exact retry schedule is a reviewable operational parameter, not a new financial policy. Transport retries use bounded exponential backoff (proposed 1s, 2s, 4s per attempt series) and then report unavailable until next scheduled cycle; data/schema failures do not enter indefinite retries.

### Application transaction and replay

`applyBatch(plan:MutationPlan, expectedEpoch:number):Promise<ReceiptResponse>` retains the frozen signature, on a service closure bound to exact immutable artifact/profile and inbox selection. It does not trust caller plan contents as authority. `runCycle(sourceRef)` returns the frozen applied/pending/quarantined summary; a richer read DTO carries receipts/progress without changing that function into a source-credential or model API.

Before transaction: load exact approved bundle/artifact/profile, validate hashes/runtime version, read current source semantics via private capability, choose explicit cycle asOf and bounded inbox selection. Missing source semantics fails closed. A declared changed/unseen event schema/semantic dependency blocks before mapping, even if its metadata feed is late. A captured governing change is sticky until reviewed; never infer approval from lexical revision order or a later equal-looking document.

Lock order for apply/status: existing `parent-scope` advisory key, current connection head, target row, global economic/record/delivery locks via `lockImportIdentities`, application outcome/progress rows in stream/event order, activity counter last. First activation retains its existing scope/import-key/target/identity order; lazy connection initialization under the same scope key reads only its committed immutable import. Capture never waits for account locks. Do not acquire new identity locks incrementally after the initial sorted set; restart selection if a discovered prerequisite changes that set.

Under lock recheck active status/expected epoch, exact artifact/profile bindings, target expected version, inbox selection and current outcomes. Recompute the plan with the same asOf and compare canonical hash/content. Check replay associations first for an exact previously committed plan, returning its byte-identical receipt even after later pause/revoke; that recovery performs no new writes. Stale target produces a hold/replan boundary, never overwrite. Reuse financial validator and checked arithmetic; reject bootstrap-only ensure operations. Insert only new economic records, append snapshot with incremented target version, move parent pointer, write receipt/lineage/outcome associations and contiguous progress/activity in one checked-out runtime transaction. Use existing three-attempt 40001/40P01 `withTransaction`; no source/model/network I/O under locks.

All-replay candidates require explicit economic equivalence and original receipt lookup. `planBatch` currently drops those candidates from plan output, so a reviewed pure classification helper or planner companion result is a dependency of this phase. Do not treat every unmentioned input as replay. Reversal support remains full payment/credit reversal only, preserving originals and reversing associated allocations at effective time; no partial/invoice/reversal-of-reversal support.

## 3. Current authority, commands and reads: separate freeze

Proposed `ConnectionStateV1` contains schemaVersion, scope, original activation ID/hash bindings, current status (`inactive|active|paused|revoked`), current epoch (0 only inactive), per-stream capture/application vector, coverage/counts/amounts, gaps, last receipt and safe error, plus `runtimeModelCalls:0` backed by isolation proof. Original ActivationStateV1 stays an historical approval/initial receipt read. Parent `asOf` and `snapshotHash` selectors retain current semantics: a new backdated event changes latest-known reconstruction, never the stored approved snapshot.

Amounts are reported by record kind and outcome, with USD and checked sums. Do not add invoices, payments and allocations into one misleading balance. Invalid/unmapped amounts contribute an unknown count, not zero cents; expose measured/unknown coverage. Unknown high-water yields unknown lag, not zero lag. B batch gaps remain visible separately from event gaps. Snapshot reads and progress reads use one consistent runtime read transaction so counts and cursors describe the same committed state.

Keep public routes from shared contracts: GET `/api/connections`, GET `/api/connections/:accountId`, POST suffix `/pause|resume|revoke`, backed by worker private GET `/internal/connections/:accountId` and POST `/internal/connections/status`. Proposed command body `{expectedEpoch:Version,idempotencyKey:Id}`; route selects action and session middleware constructs ReviewerContext. Private DTO additionally carries exact scope, action and authenticated actor. No product tool may invoke it. Require CSRF/session/source/account authorization and no-store; worker requires separate service capability. Scoped list pagination and gap detail pagination must be bounded and deterministic. Errors use ApiError with malformed400, unauthorized401/403, unknown404, stale/conflict409, semantic block422, unavailable503; no raw SQL/body/stack.

Technical transition proposal: initialize current head active/epoch1 from committed A5 import. A real active→paused, paused→active or active/paused→revoked transition increments epoch using checked addition; exact command replay returns original result, key/content conflict409, stale expected epoch409. Same-state new request is a no-op result (no epoch change). Revoked→active/paused is forbidden. Resume requires exact unchanged pinned artifact/profile/schema and current approved semantics, and does not clear unresolved data holds. Apply and status serialize on the same head: if revoke commits first, old-epoch apply cannot commit; if apply commits first its receipt predates revocation and remains recoverable. No claim that a revocation undoes prior effects.

**This transition/DTO proposal needs exact design review before implementation.** Specs establish pause/resume/revoke and epoch fencing, but do not freeze their command idempotency shape or epoch increment convention. These are technical choices; if an owner identifies a conflicting accepted authority rule, resolve that conflict before dispatch. Reenrollment and version switching require a later design because runtime002 permits only one initial import per account. P3 must not evade that constraint by updating immutable activation rows.

## 4. Semantic/evidence and privacy boundary

Financial events declare schemaVersion and semanticVersion. Compare to pinned contracts/profile before writes regardless of metadata arrival order. Baseline semantics and seen semantic events are durable facts, not a newly granted revision. Declared scoped governing changes hold the mapped customer; unscoped governing changes or unsafe identity pause source application. Unknown-account financial events remain unassigned holds while known independent accounts progress.

New PDF/email/contract arrivals are evidence, not new executable financial kinds. Existing current-semantics API returns revisions, not a complete document-arrival catalog. Source producer must demonstrate that every required governing arrival publishes its declared revision/manifest notification, with source-wide stop when account association is unsafe, before P3 can claim document drift coverage. Do not teach worker to interpret PDFs or silently add an event kind to frozen RawSourceEvent. Undeclared same-shape semantic changes remain PRD §13's explicit limitation.

Publish F7 events in the owning runtime transaction: source.captured, event.pending/quarantined, batch.applied/replayed, connection.paused/revoked, plus an allowlisted resumed summary if frozen. Only IDs/hashes, counts, cents with coverage, status and diagnostic codes. No credentials, raw environment, paths, source documents, protected expected outputs or hidden reasoning. Continue existing composite control/runtime SSE cursor protocol; replay invalidates/refetches authoritative reads and must not double-increment UI counts. Source-wide unknown holds are visible only with source-wide read authority, never leaked via an unrelated customer's detail.

## 6. Required new-input and failure proof matrix

| Scenario | Required observation |
| --- | --- |
| A approval window | Publish actual new source events after reviewed snapshot but before activation; first cycle starts strictly after bound S and imports them once. |
| A AI-off payment | After activation and worker model isolation, operator injects fresh $300 payment **and explicit allocation**. Current balance 80000→50000 cents; original approved cutover snapshot remains 80000. An unallocated $300 payment alone leaves invoice balance unchanged. |
| A new invoice | Fresh operator source-issued invoice absent from baseline and cached capture appears through source transport/inbox/receipt, with exact derived balance increase. |
| B AI-off input | Fresh complete CSV batch and receipt API input after each own baseline cursor; exact original byte hash, batch sequence and event vector preserved; explicit allocations determine balance. |
| CSV gap | Producer advertises batch N+2 while N+1 absent; worker shows batch gap and does not advance contiguous batch coverage. Arrival of N+1 permits ordered capture. Cannot substitute an upload409 or fake worker counter for this proof. |
| Missing dependency | Capture payment/allocation first, later invoice in another page/stream; pending gap remains visible, later prerequisite can be ingested and applied in validated group; absent/cyclic dependency has no fund consumption. |
| Replay/version | Identical delivery and new delivery with identical economic identity produce original associations, stable record IDs and one effect; changed economics under same identity held across artifact versions. |
| Semantic ordering | Financial event with unseen/changed revision arrives before metadata: held before write. Known scoped change does not block independent customer; unscoped change blocks source. |
| Crash/race | Deterministic test barriers at page commit and monetary commit; process restart recovers durable pending work, committed receipts and exact checkpoints. Two capturers/applicators cannot double-apply. |
| Revocation | Barrier between preparation and lock/recheck; revoke wins, old epoch cannot commit. Apply wins first, then revoke leaves prior receipt recoverable and prevents new writes. |
| Target/history | External expected-version conflict holds; backdated latest reconstruction differs from original approved snapshot without modifying history. |
