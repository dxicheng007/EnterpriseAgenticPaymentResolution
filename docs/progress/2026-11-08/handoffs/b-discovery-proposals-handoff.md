## Routine representation choices (fixed here)

New proposal ID is server randomUUID once per validated publication plan, reused for the selected step's commit. Same-step replay returns stored result before evidence I/O. New preflight of an uncommitted step may allocate a new representation ID; nothing may externally observe a preflight ID.

Persist `submitted` as the strict parsed input (model semantic content unchanged; schema-declared set ordering is canonical). Store server `DiscoveryProposalV2` in `payload` and `hashCanonical(payload)` in `payload_hash`.

Namespace only representation IDs:

- Stored spec.id = `discovery-spec:` + `hashCanonical({runId,submittedSpecId:input.spec.id})`; stored spec.version = submitted spec.version. For every historical proposal in the run, same **submitted** spec.id/version must mean identical canonical submitted spec bytes. Different body at same pair conflicts, including within a batch. Same company spec can be reused by separate customer proposals. No automatic spec version bump.
- Stored profile.id = `discovery-profile:` + `hashCanonical({runId,proposalId})`; stored profile.version = proposal revision. All other draft fields remain exactly submitted; then compute hashProfile and validate full current CustomerProfile. The submitted input plus stored payload is the explicit immutable identity mapping; no extra DDL/hidden lookup is needed.
- Never rewrite scope.accountId, parentCustomerId, bootstrap customer/configuration IDs, seller, source aliases, lookup targets, contract/term IDs, mappings, amounts, effective times or semanticVersion. These are proposed semantic content, not namespace bookkeeping. Profile ID/version rewriting preserves no claim of financial identity approval. Pending v1 findings stay pending; do not synthesize them from sidecars.

## Evidence preparation and authorization

`prepareProposalEvidence({binding,sourceRead,input}, tools): Promise<PreparedProposalEvidence | DiscoveryReadToolFailure>` lives in proposal-evidence.ts. `PreparedProposalEvidence` contains `{facts:CaptureFacts, contracts:SourceContract[], streams:CaptureStream[], accountSubjects:source_account[], diagnosticCodes:string[]}`. Data is detached, server-prepared and never model-supplied. No source package change or new capture service is required.

Call describeSource through existing prepare port and validate exact binding/facts and success schema. Require submitted sourceRef/company to match capture; every profile alias uses profile.scope.sellerEntityId and must occur in facts.sourceAccounts and saved task sourceRead grant. Source-wide connector tasks can submit a profile before any parent account grant exists; account-limited tasks cannot add an alias outside their exact granted tuples. Proposal creation does not add allowedAccountIds. Require submitted sourceContracts and capture streams equal pinned described contracts/streams canonically; reject fabricated resource schema, version or stream. Preserve authentic compile-time mapping validation for C3: do not invoke compile in C2 or reject a schema-valid unsupported mapping using an ad hoc compiler.

Enumerate refs using the actual executable shapes (no nonexistent profile.evidenceRefs field): spec.evidenceRefs, each mapping operation's constant evidenceRef, each approvedLookup entry.evidenceRefs, contractTerms.evidenceRefs, v1 findings' evidenceRefs (v1 has no alternatives field) and bootstrap.customer.evidenceRefs when present. Walk only the frozen MappingOp union, not arbitrary JSON key names. Validate every citation through accepted readEvidence preparation under task grant, with the same small prefix/surrogate retry as C1 if needed; validate all returned facts equal the pinned complete capture. There is no model-supplied citation object/hash/excerpt to trust here: these fields are IDs. For sidecar refs use authorized readFinding in the owner transaction.

Preserve citation provenance by its containing field and source/account purpose. Source contract/spec citations can be source-level; do not require every schema citation to prove every customer. Account alias identity is established only by captured tuple membership plus cited lookup/identity observations, not by a display-name match. Use paginated account querySnapshot event/citation associations for each exact proposed tuple, preserving seller collisions. An alias must have nonempty cited proposed parent-account lookup entry with `source` exactly that alias and `target` exactly scope.accountId; verify readability and association. This is structural evidence linkage, not acceptance that the proposed parent ID is correct. Lookup items of valueType text do not grant identity.

For account-bound terms/bootstrap/v1 finding references, check captured event association against the profile alias tuple set where that association is available. Readable documents whose account applicability cannot be established by existing source proof must remain inspectable drafts with assessment diagnostic `PROPOSAL_EVIDENCE_APPLICABILITY_UNRESOLVED`; do not use document contents, filename, coverage UI or model claim as an authorization proof. Forbidden citations reject the whole batch; unknown applicability with authorized source-wide read is a blocked draft. Source-wide access does not establish semantic support for a monthly fee. A source account lacking usable identity evidence similarly yields the same blocking assessment diagnostic rather than filled-in identity data; a nonexistent/ungranted tuple rejects. This is the conservative unresolved-applicability behavior already specified, not a new evidence oracle.

Retain all compiler validation for C3 (e.g. missing term citation, pending material v1 finding, wrong approved lookup semantics beyond the evidence linkage above). C2 may persist such structurally valid drafts and source applicability diagnostics; it must not call them compiled/eligible or silently repair missing content.
