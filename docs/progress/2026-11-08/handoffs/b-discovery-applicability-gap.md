# Discovery document applicability prerequisite — design finding

**Conclusion:** Current event/citation association cannot establish applicability of either company's agreement PDF citations. Genuine A/B proposals that cite the agreement for account identity, monthly terms and bootstrap customer name will remain blocked under C2. This is an expected missing prerequisite, not a reason to weaken C2 or substitute development candidates. C2 persistence can proceed.

## Concrete code evidence

- `scripts/generate-fixtures.ts:201` and `:312` emit each A/B agreement as a separate `contract_pdf`, with explicit seller, buyer, account, legal name and monthly fee. A's text orders fee then `Effective ...`; B orders `fee ... effective ...`. These files are not event batches.
- `apps/control/src/demo-candidates.ts:126` onward uses the captured agreement citation for the account-map entry, contract term and `bootstrap.customer.evidenceRefs`. It parses that document and deliberately constructs a **development** candidate. Discovery must not import this builder or accept its output as model construction.
- `packages/sources/src/discovery-tools.ts:87–143`: captured API citations have event.rawIdentity; **all file citations are assigned identities:[]**. `eventEvidence` associates API citations and exact CSV `payload_json` batch rows. PDFs and email documents do not enter the event→citation map.
- `packages/evidence/src/search.ts:19` and `packages/sources/src/evidence-records.ts:32` preserve the consequence: source-wide authorized readers can inspect a document, but account-limited readers cannot claim unknown document coverage. A text range does not change that.
- `packages/discovery/src/construction-evidence.ts` consumes querySnapshot event evidence IDs. A PDF citation remains in its missing set regardless of pagination, so an account finding based on that document is `applicable:false` and raises the durable source-wide `FINDING_APPLICABILITY_UNRESOLVED` origin. C2's proposal-specific applicability diagnostic has the same limitation. An event citation can prove the raw account tuple exists; it does not prove the agreement fee/name applies to it.

**Small example:** let `Epdf` be the captured page-one citation for A's first generated agreement and `A1` the seller/account printed in it. A source-wide connector reads `Epdf`, then submits account-map `{source:A1,target:<proposed account>,evidenceRefs:[Epdf]}`, a cited monthly contract term and bootstrap legal name. `querySnapshot({account:A1,...})` returns API event citations, never `Epdf`. The model may have interpreted the PDF correctly; current server association proof is still missing. B's first agreement behaves identically: B CSV row citations can establish event association, but its separate `b-contract-1.pdf` citation is not a CSV row. Replacing Epdf with an invoice/event citation merely to pass the association test would leave contract/name support unproved and must not become the successful fixture.

## Existing specified path and its limit

There is already a **source-owned observation implementation**: `packages/sources/src/source-coverage.ts:91` `deriveSourceCoverageObservations`, called by `readSourceCoverage(...,exactSnapshotId,authorize)` at line387. It checks captured bytes/membership, recognizes the exact full A/B agreement formats, extracts seller/account/sourceBuyerId/legal name, detects conflicting agreement/directory claims, and returns agreement IDs as `identityEvidenceRefs`. The accepted `docs/progress/2026-11-08/handoffs/guided-discovery-implementation.md` defines this as `captured-source-rules-v1`, explicitly source-side identity observations, not parent identity/financial approval. Thus the raw documents and narrowly supported parsing facts needed for ordinary unambiguous A/B identity association already exist; a key/provider cannot fill the missing server integration.

However **that coverage response is not a discovery capability or per-excerpt complete exposure proof**. The accepted evidence-tools handoff explicitly excludes the coverage display parser as authority. It does not produce the exact citation/range→all-exposed-identities proof required by permitsEvidence, does not attest every contract amount/effective interval, and is not wired into finding/proposal applicability. In particular, a directory may expose several accounts and an amendment may identify buyer/contract without an explicit account; a UI account row cannot grant access to the entire document. No existing accepted API can simply be called to clear the current blocker.

The accepted orchestration specification §4 already permits an account-limited document read **if a source-owned coverage extractor actually proves every exposed identity**; unknown coverage remains denied. The next narrow prerequisite is therefore a separately assigned source-owned document/citation applicability proof and trusted consumer integration, with exact immutable binding/locator/hash and fail-closed ambiguity checks. It can reuse proven extraction primitives after source-owner review, but must not relabel the UI response as authority. Initially source-wide tasks could consume an explicit trusted applicability proof without widening any account-limited read; separate whole-document/range authorization still requires complete exposure proof. Root/source owner must freeze that exact port and tests before implementation. This is a technical implementation/authority-boundary prerequisite for unambiguous supported formats, not permission to add financial rules or a requirement to ask the user to approve an obvious parsed seller/account tuple.

Required later evidence includes both original A/B formats, changed names/accounts/amounts, seller collisions, multi-account documents, contradictory directory/agreement, unsupported prose, exact capture/hash/locator mismatch, and account-limited disclosure denial. It proves document association only; protected evidence/financial/bootstrap verification must still independently check proposed terms and metadata. C3 registry publication alone will not solve it.

## Material gaps that remain separate

- PRD §12 permits reviewer-confirmed inferred identity/schema relationships, but requires applicable observed/derived amounts and says approval cannot make unsupported amounts factual. The accepted discovery spec provides **no reviewer tool that clears sticky finding contradiction/applicability origins**. Later source proof or an agent-supported revision cannot erase an old C1 origin; plan a fresh run after the prerequisite is available, unless a separately specified reviewer-resolution workflow is approved.
- Ambiguous buyer/contract-to-account association, contradictory documents, unsupported amendment/effective-time interpretation or missing financial support must remain blocked. If successful acceptance requires choosing among such interpretations, source-owner specification search precedes user clarification of the exact missing material behavior. Do not invent a coverage rule, auto-confirm pending facts, or borrow protected truth.
- Proposed sourceBuyerId→parentCustomerId and new parent-account preview/verification capabilities are separate existing unresolved authorization/identity boundaries. A document association proof does not grant them.

**Action for root:** carry document applicability proof as an explicit prerequisite before claiming successful genuine A/B V4 candidates, independently of C2 and provider hookup. C2 remains a valid pending/blocked-proposal slice. No source edits, implementation, tests, commits or subagents in this diagnostic. The already-written C2 brief's future C3 snapshot correction remains valid; no additional C3 scope is introduced here.
