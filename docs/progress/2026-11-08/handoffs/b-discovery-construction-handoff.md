- Keep immutable evidence, agent interpretations, pending profiles and imported records distinct. Citation validity is not semantic verification.

### Contracts and private interfaces

Publish `PublishFindingInputSchema`, `ReadFindingInputSchema`, `PublishFindingResultSchema`, `ReadFindingResultSchema`, inferred types and `discoveryFindingToolSchemas`. Inputs exactly match accepted tool table:

- publishFinding `{findingId?:Id,expectedRevision:0..N,subject,fieldPath,value,provenanceClass,evidenceStatus,evidenceRefs,derivationInputs,alternatives,unresolvedQuestions}`. Reuse DiscoveryFindingV2 field validation, canonical JSON/depth and set handling; do not duplicate weaker JSON parsers. New identity requires absent findingId and expectedRevision=0; revision requires existing same-run identity and exact current expectedRevision. An unknown supplied ID does not create an identity.
- readFinding `{findingId,revision}` → `{ok:true,finding:DiscoveryFindingV2}` or existing closed safe failure envelope.
- publish success `{ok:true,findingId,revision}`; server builds and validates the complete DiscoveryFindingV2. Failures use existing DISCOVERY_INVALID/FORBIDDEN/CONFLICT, SOURCE_UNAVAILABLE, TOOL_RESULT_LIMIT and unavailable/forbidden behavior; limit exhaustion persists a safe blocker (specific finding budget diagnostic constants are implementation bookkeeping and must be tested).

New private evidence helper: `prepareFindingEvidence({binding,sourceRead,input}, readTools): Promise<PreparedFindingEvidence>` where input is parsed PublishFindingInput and output contains detached CaptureFacts, authorized citation identities and association proof for all direct/alternative evidence refs. It is not a tool and cannot widen grants. Use the accepted source-owned prepare port and complete immutable capture validation. Do not treat membership-only CaptureFacts as account applicability proof. QuerySnapshot's validated event/citation association can prove exact seller/account association; document-only citations lacking proven account coverage cannot establish it. A bounded readEvidence range is permissible for checking citation readability without requiring full long text; it does not establish coverage or new semantics. No full-document text or hidden truth stored in findings.

In findings.ts define SQL-only operations using the *provided owner PoolClient*: `validateFindingPublication(client, context, input, prepared)` → validated write plan, `publishFinding(client, context, plan)` → typed success; `readFinding(client, context, input)` → typed exact revision. Context is internal persisted `{run,task,step}` loaded by supervisor; no caller-manufactured grant/context. Do not export a second unauthenticated service entry point. No pool transaction inside these operations.

### Persistence and interpretation

Store identity/run/investigation/current revision separately from immutable revision payloads. Composite same-run FKs bind publication task, toolStepId, identity and exact derivation revisions; unique publication toolStepId prevents duplicate revisions. Store originating investigation/subject and a durable unresolved blocker-origin ledger, including original finding revision. App role gets SELECT/INSERT on immutable revisions/edges/blocker origins, narrowly scoped UPDATE for current pointers/counters; no UPDATE/DELETE of immutable payloads. Use existing run lock and unique stable source/account investigation keys. No source capture or runtime writes.

**Exact table ownership in007:** discovery owns `discovery_finding_identities` (run/investigation/current pointer), `discovery_finding_revisions` (append-only complete payload/publication step), `discovery_finding_derivations` (exact same-run revision edges), `discovery_finding_blockers` (append-only origin plus applicability investigation/code), `discovery_proposal_identities` (run/current pointer and logical identity), `discovery_proposal_revisions` (append-only submitted and server-hashed payload/publication step), `discovery_proposal_findings` (exact consumed refs), `discovery_proposal_investigations` (append-only union binding), `discovery_proposal_assessments` (append-only versioned assessment payload), `discovery_proposal_current` (current result/assessment link, invalidated under run lock), and `discovery_compile_steps` (tool-step keyed exact subject, reserved/registered/settled state and historical result). Composite FKs enforce same-run ownership throughout; unique step bindings and proposal revision/assessment identities are mandatory. Spec ID/version canonical consistency and current alias/account collisions are checked under the run lock against stored proposal content; no new financial identity tables. Keep compile-step source payload immutable and permit only narrowly scoped state/result updates. C1 migration tests prove all constraints/grants, including proposal/compile tables, while C1 runtime only uses findings tables. C2/C3 runtime activation is separately reviewed, so unused tables cannot advertise tools. This is concrete future checkpoint storage in one migration, not a no-op reservation. If the implementer finds these columns cannot express a specified fence, send the exact schema adjustment to root before freeze; after007 lands, never edit its bytes.

Maximum 100 finding identities and 10 revisions each **per investigation**. Reserve/count under the run lock, including same-batch writes; a new task, alternate ID or superseding revision cannot reset counters. Bind publication subject to its task investigation. Cross-subject mutation cannot relocate an identity or shed blocker applicability. Cross-run references fail; readFinding requires current task grant for the referenced finding subject and all exposed citations/derivation content, not merely same run. Retain exact historical revisions after supersession.

Every derivation input is an existing exact revision in the same run and authorized to this task. Check the persisted identity/revision graph for self-reference/cycles and dangling edges; provenance claims cannot invent derivation inputs. Publishing consumes exact immutable historical references, while proposals later must consume current finding revisions. Do not require all publication derivation refs to be latest: the accepted spec requires exact existing revisions here. No automatic calculation or confirmation of a model-supplied derived value.

Every contradicted/insufficient/inferred/unresolved finding creates durable potentially material blocker provenance. Supported/observed or supported/derived is still an agent assertion. If captured evidence association does not establish claimed applicability, retain `FINDING_APPLICABILITY_UNRESOLVED` in the source-wide blocker set, without promoting or guessing account applicability. A forbidden citation remains a rejected call, not a stored claim. Source-subject findings apply to every proposal. Keep `FINDING_RESOLUTION_PENDING` origins even after a supported revision/new ID; no model tool resolves them. Persist exact origin refs, not just strings in run.diagnostics. C1 creates the ledger C2/C3 assess; it does not invent a reviewer resolution API.
