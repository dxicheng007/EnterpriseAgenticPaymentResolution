# Bounded atomic ongoing-apply design

**Status:** Design preparation only, for fresh independent review. Not an implementation plan, path/DDL reservation, implemented feature, machine pass, independent acceptance or joint user acceptance. Prepared against integration HEAD `8b50c9cfb231ab3d64391cef877df75fe78c82b0`. Round1 repair pins independently accepted classifier candidate `ec91a4bae74ab22623ed5cdeaf55f4de07e085a6` and its [exact-candidate review](../reviews/platform-sync-classification-ec91a4b-review.md). PR36's pure dependency helpers remain unaccepted dependencies and are not assumed here. Concurrent code/test/review edits were left untouched.

**Intent:** Make one already authorized customer's deterministic financial apply unit atomic with its authoritative receipt, economic/delivery associations, event outcomes and application progress, while preserving original approval history and runtime-only authority. Keep the first increment narrow enough to prove this transaction without implementing a scheduler or deciding unresolved progress policy.

**Architecture:** The existing worker owns one checked-out runtime PostgreSQL connection per transaction. It reuses the accepted current-authority fence, immutable capture, existing compiler/finance calculation and parent snapshot primitives. Control remains non-authoritative; no control database, model call, SDK, key, new authority ingress or product route enters this design. Existing Node24, strict TypeScript, PostgreSQL18/pg and Vitest suffice.

## 2. Hard boundaries and dependencies

- Standing authority comes only from the exact committed A5 import, selected profile and immutable bundle. Source capture, classification, registry registration, an active-looking DTO or a caller-supplied plan grants none.
- The original activation, epoch1 receipt, approved snapshot, profile/artifact/manifest, source originals and initial associations remain unchanged. Current authority is a separate head. New receipts use the current locked epoch and the original activation ID; they never rewrite the original activation epoch.
- F1 global delivery identity is `(sourceRef,eventId)`; economic identity is `(sourceRef,sellerEntityId,kind,recordId)`. Account aliases, versions and new event IDs do not create money. Canonical delivery checks include observedAt. Global position identity remains capture-owned.
- The only monetary interpreter is the existing compiler/finance pipeline. Reuse its mapping, economic equivalence, dependency grouping, checked arithmetic, full payment/credit reversals and explicit allocations. No worker-side comparator that drops additional fields, guessed allocation, correction posting, ensure operation, update/delete or invoice issuance.
- Approved allowedKinds and limits remain exact. Enforce the selected grant's limits and the compiler bound, without relaxing either; the frozen maximum is 1,000 input events and 5,000,000 cents per transaction. Count replay/coalesced/repeated occurrences under the existing compiler rules. Never split a coupled group to fit.
- Capture remains independent. Apply does not fetch, ingest, advance capture cursors, acquire capture lane/stream/checkpoint locks or rewrite deliveries. CSV lanes are not supported by accepted capture; no Company B recurring-export claim follows from this design.
- Required before writer dispatch: retain the independently accepted classifier pin and exact contract; independent review of this repaired design including bounded coverage; any genuinely new resolution authority in §8 settled for expanded scope; integrator-owned catalog/path reservation after rechecking concurrent branches. PR36 cannot supply any required dependency by assumption.

## 3. Classification is candidate metadata, not authoritative apply

Consume the independently accepted `ec91a4b` compiler companion on the existing `@eapr/compiler/plan-batch` subpath. Its target/artifact/profile/asOf binding and exhaustive original-input mapping are recomputation evidence. They are not signed authority, globally unique economics, a receipt lookup, a durable outcome or a resolved progress marker.

| Classifier result | Required runtime interpretation |
| --- | --- |
| `not_classified`, held group or source blocker | No successful monetary unit or frontier advancement from that result. No missing-item inference. A held member cannot be relabeled replay merely because a target record exists. |
| `financial_new` | Proposed exact plan operation. Under global identity locks prove it is genuinely absent from all parent accounts and has no original economic association. |
| `financial_replay` | Equivalent to the selected validated target record. Under lock resolve and validate that record's original initial-or-ongoing receipt. Missing, mismatched or multiple origin associations are storage inconsistency, not permission to mint a receipt. |
| `financial_coalesced` | Points to this unit's producer operation; it will share that operation's receipt if the transaction commits. It has no prior receipt just because another input has identical economics. |
| `delivery_repeat` | Follow the checked representative, write one delivery outcome, never count another ledger event or financial record. |
| `semantic_observed` | Nonfinancial observation only. It does not grant a revision, clear a sticky drift hold or resolve an application frontier under an unstated rule. Excluded from the first writer increment. |

Recompute from exact immutable inbox deliveries and the locked authoritative target, with the chosen explicit asOf. Compare full canonical plan and hash, not a caller's classification labels. Validate classifier index/event/group references and exact plan/op correspondence as consistency checks; do not remap raw monetary fields in runtime.

A classification invocation can contain multiple accepted dependency groups while legacy `PlanOutcome` emits a combined plan. Group indices are not receipt boundaries. Never cut operations/eventIds/lineage out of that plan to manufacture per-group plans. First increment accepts exactly one complete accepted financial dependency group; its independently recomputed nonempty plan is the apply unit. Later multi-group orchestration must replan each complete selected unit against the target version it will actually commit, or separately review an atomic combined-unit contract.

## 4. Exact receipt and economic associations

F5 distinguishes original economic effect from the event membership of a later mixed receipt. Preserve both facts explicitly:

1. **Economic origin:** Each stored financial record has exactly one original receipt that first created it, initial or ongoing. Original record ID, sourceEventId, sourceRecordVersion and canonical bytes remain unchanged on replay. Existing `runtime_economic_outcomes` rows retain their initial import reference.
2. **Delivery effect association:** Every newly acknowledged financial delivery identifies its economic record and that record's original receipt. A new event ID replaying an initial import therefore points to the initial receipt, even if acknowledged in a later mixed transaction. Existing delivery associations are never rebound.
3. **Apply-unit acknowledgment membership:** A nonempty mixed receipt includes all distinct acknowledged financial event IDs from its exact recomputed plan, including equivalent replay and coalesced inputs. Membership in this receipt describes the unit's acknowledgment, not ownership of every listed event's original monetary effect. New record target IDs are exactly the financial operation IDs in plan order; replayed existing record IDs are recoverable through associations, not fabricated as new writes.

Example: initial receipt R0 created payment P. A later complete group contains new delivery E1 of equivalent P and new allocation A delivered as E2. New nonempty receipt R1 acknowledges E1 and E2 and has A's target ID. P's economic origin and E1's effect association point to R0; A's origin and E2's effect association point to R1. R1's membership includes both events. Nothing rewrites R0 or P. If another new delivery of A coalesces into the group, it also points to A/R1 and appears in R1 event membership, with only one A insertion.

An already acknowledged exact delivery may be listed in a new mixed plan if the unchanged planner returns it; retain its original outcome/association and add only the new unit membership. Canonical delivery conflicts fail before any benign replay result. Global economics found under another account/scope cannot become a selected-account replay or be inserted anew.

**All replay:** No new snapshot, target version, financial record, plan receipt or lineage for nonexistent operations. Under active current authority, persist any newly acknowledged delivery outcomes and the eligible contiguous financial progress in the same transaction, each referring to its original receipt. An internal cycle/event-association read may return multiple originals. Do not force these into `ReceiptResponse` or manufacture a zero-effect monetary receipt. The frozen `applyBatch(plan,expectedEpoch):Promise<ReceiptResponse>` remains for one nonempty mutation unit or exact previously committed plan replay only; all-replay bookkeeping is a separate internal operation whose concrete interface needs the later plan.

**Exact committed-plan recovery:** Look up the immutable scoped plan association and compare full canonical plan/request binding before active/stale-target checks or source preflight. Return the stored receipt byte-for-byte with replayed=true even after pause/revoke or later target changes. This is a read-only recovery of an existing operation, with current caller read authorization when eventually exposed. Do not recompute against today's target and replace an old receipt. Do not change delivery outcomes/progress or publish a second successful activity on exact recovery.

New monetary receipt fields use existing `SyncReceipt`: original activationId; current locked epoch; exact scope and artifactHash; exact recomputed planHash/eventIds; operation-derived targetRecordIds; before/after balance at plan.asOf; status applied; committedAt chosen once for the successful attempt. Persist plan, profile/bundle/manifest bindings, explicit asOf, before/after snapshot hashes and versions, and lineage as companion audit data. A plan hash is an integrity subject, not authorization. Proposed technical replay namespace is `(original activationId,planHash)` with canonical equality checked; expected epoch of the successful operation is stored with the association, not supplied to reinterpret the receipt later.

### Additive persistence obligations, without DDL reservation

Existing runtime002 economic/delivery outcomes and import lineage FK specifically to `runtime_activation_imports`; do not insert ongoing receipts there or modify those historical tables in place. Additive storage must represent ongoing receipts/plans/lineage, original ongoing economic associations, new delivery effect associations, apply-unit event membership, scoped immutable outcomes and application heads. These are responsibilities, not reserved table names or files.

Use scoped, noncascading enforced foreign keys to actual original receipt rows. An initial/ongoing reference can use separate typed nullable FK columns with an exactly-one check, not an unchecked polymorphic receipt ID. Preserve existing initial rows; resolve origin by validating the initial and ongoing domains together. Reject ambiguity, missing receipt, mismatched scope/identity/record or corrupt canonical bytes. Global `parent_financial_records` uniqueness plus the complete identity lock set prevents a second economic domain; the later DDL review must prove cross-domain association exclusivity rather than rely on a union query alone. Do not backfill missing original ownership from a target balance or guessed receipt.

Receipt, plan, event membership, outcomes and lineage are immutable canonical histories with digests and validated scalar indexes. Mutable heads contain only reviewed progress pointers/version fields. Application roles receive minimum scoped writes, no history UPDATE/DELETE/TRUNCATE. All ongoing FKs retain the original grant/history. SQL relationships enforce scope and record references; application canonical validation additionally verifies plan/receipt/economics and hashes. No mutable head silently reconstructs progress after its history exists but its head is missing.

## 5. Transaction boundary and lock order

Before opening a write transaction, bind a bounded immutable selection to the genuine committed grant and lane, choose explicit cycle asOf, recover exact committed work when present, validate artifact/profile/runtime hashes, and obtain current semantic observation through the existing worker-owned private capability. Reuse the exact selected-profile equality rules; no caller-supplied observation or newly invented TTL. Source fetch/observation, filesystem I/O and clocks used by preparation stay outside SQL locks; inject the commit instant rather than let pure calculation read wall time. Current operator activation setup files or new evaluator runs are not a substitute for, or prerequisite to recover, the committed grant.

For new work, current-source preflight and each event's approved schema/semantic dependencies are both required. At the authoritative captured-input cut defined below, any source-wide governing blocker or selected-customer drift prevents new application; an unapproved/missing revision is not a harmless gap. Other known customer revisions must not be interpreted as selected-customer drift. The narrow increment may reject their unsupported coverage, without treating that as source-wide semantic failure or claiming independent-customer scheduling. Current-semantics equality alone cannot erase a previously captured sticky change. No claim of atomic external source/runtime observation or comprehensive document-feed coverage is made.

### Bounded coverage witness and concurrent-capture boundary

This is an explicit technical narrowing of the unmounted primitive, not a general hold/clearance fence. Let B be the exact committed manifest's stream baseline vector, F the selected customer's stored application vector (initially B), and C the complete capture-checkpoint vector read for the lane. For this first increment the manifest must declare exactly two streams: one financial api stream S and one semantic stream; any other stream shape is unsupported coverage, without changing the accepted source contracts. Before any new successful apply or replay-bookkeeping transaction, require all of the following from actual runtime storage, not the caller or fixture:

1. Exactly one initialized `runtime_capture_lanes` row exists for this source and it is the committed manifest lane. Its canonical manifest/capture definitions match the committed bundle and contain only accepted api/semantic transports. Checkpoints are exactly its declared stream set with exact B baselines. No global `runtime_source_positions` for this source uses an undeclared stream. Additional lanes or source positions not representable by this lane make coverage unavailable; they are not assumed irrelevant. This intentionally excludes general shared-baseline/backfill orchestration.
2. For every stream T other than S, C[T]=B[T] and F[T]=B[T]; there are no post-baseline global positions, inbox rows or pages for T. Thus even an unchanged post-baseline semantic event is unsupported coverage, rather than silently declared resolved. This predicate excludes a governing change followed by a later return to the approved revision: the immutable change history still exists and causes rejection.
3. S has a complete contiguous stored history `(B[S],C[S]]`. Its count N=C[S]-B[S] uses checked integer arithmetic and must be at most 1,000 **across the entire retained post-baseline history**, not merely this invocation's suffix. Every position has exactly matching global position/delivery, lane inbox and complete-page membership; canonical page/event hashes and range/count bindings validate. The verified pages chain exactly from B[S] to C[S], with no hidden prefix/suffix/gap. Reject any source-global selected-stream position or lane inbox/page beyond C[S], or any missing corresponding position inside the interval; do not scope the global-position query to already matching inbox rows and thereby hide orphans. Every history event is financial and its raw identity resolves through the exact approved profile to this selected scope; any semantic/unknown/foreign-scope/malformed member makes this narrow coverage unavailable. Immutable approved baseline members are validated through accepted committed/capture bindings; they are not reclassified as new input or counted as ongoing progress.
4. Every history position in `(B[S],F[S]]` has its immutable successful outcome and validated original receipt association under this grant/lane; no absent, pending, quarantined or otherwise unresolved position may be crossed. Source-wide incident presence for this source is also unsupported for this first increment: a bounded EXISTS check rejects it, without deciding a future incident-resolution policy. The remaining entire suffix `(F[S],C[S]]` is the selected input—no smaller caller-selected prefix can hide later captured work. It is nonempty, within approved/compiler limits and forms exactly one complete accepted financial dependency group, with prerequisites in the locked target or suffix. No held/unclassified result is admissible. For F=C, only already-committed operation recovery is available; there is no new monetary receipt or successful empty cycle.

Read this evidence as a **single SQL statement snapshot**: lane cardinality, declared streams, checkpoint vector, out-of-lane/stream/incident existence, and the bounded source-global positions joined to exact inbox/delivery/page history. This prevents a collection of READ COMMITTED SELECTs from constructing a coverage vector that never existed. Fetch at most 1,001 history rows and at most 1,001 nonempty page rows; the extra row is only overflow detection. Obtain lane cardinality with LIMIT 2 and unexpected-row checks with EXISTS. The exact two-stream restriction and N establish expected cardinalities before decoding the bounded rows; fetch at most three checkpoints and reject any third/unexpected row. Never truncate a result and call it complete. Canonical bytes/digests and exact counts, not absence from a limited page, prove coverage. The later SQL plan must preserve this single-statement snapshot and result bounds; it must not replace them with an unbounded table scan returned to the worker.

Preparation obtains witness W before planning. Under the authority and target locks, the transaction obtains a fresh witness W' using the same single-statement query, before using classifier acceptance or changing any financial/outcome/progress state. Include full source/lane/stream identity, B/C, canonical page and event bindings and incident/extra-lane predicates in witness equality. Also bind/check F and exact historical outcomes under the same account transaction. W' must equal W, and both must satisfy the predicate. Any changed capture vector, additional lane/position, new incident or unsupported history aborts this attempt with coverage changed/unavailable and **zero apply effects**; bounded retries cannot silently adopt a changed selection. Fresh preparation may be attempted by a later caller. Immutable source rows from W' may then be validated by exact keys; mutable capture state is not consulted piecemeal to widen W'. Persist W' or its exact bounded canonical audit binding with the committed unit/bookkeeping operation, distinct from financial plan authority.

The observation boundary is the W' statement snapshot under account locks, **not monetary commit time**. Capture committed before that snapshot is included and must pass; a page transaction that commits afterward is later input outside this attempted unit, even if it commits before the financial transaction. It cannot be acknowledged, counted or advance application progress in this unit. The next new-work attempt must obtain a new witness; a subsequently captured semantic/foreign-scope/gap/incident makes the narrow predicate fail. A source event's declared schema/semantic dependencies and the independent preflight still protect the selected events; this boundary is not a claim to atomically observe uncommitted/future source changes or to forget sticky captured history.

This design deliberately promises no stronger “no relevant capture may commit between W' and monetary commit” fence. Accepted capture has no application hold fence, and apply takes no capture checkpoint/global-stream lock. If independent review requires that stronger ordering for a later mounted service, design and review a shared capture/apply fence separately before claiming it; do not retrofit one implicitly, broaden runtime004, or acquire reverse-order locks here. The bounded SQL cut must itself receive scoped review before implementation planning; fixture emptiness is not its evidence.

One `withTransaction` callback performs the following, reacquiring every token on every attempt:

1. `lockCurrentAuthority(client, exactCommittedIdentity)` acquires existing `parent-scope` advisory lock and resolves/materializes only the genuine current head, then locks it FOR UPDATE. Preserve missing-head-with-command-history failure. Do not call the first-import writer or take its activation idempotency key as an ongoing key.
2. Under that head, recheck an exact stored apply association for lost-response/concurrent recovery. Otherwise call `assertActiveAuthority(client,locked,expectedEpoch)` and verify exact source, scope, activation/bundle/artifact/profile/manifest pins, allowed kinds and limits. Hold head until commit; a token on a pooled client is not a live-transaction detector.
3. Lock existing parent target row, read/validate exact current snapshot and expected version, then obtain and compare W' using the coverage query above. Reject changed/unavailable coverage; verify immutable inbox/lane/position membership for the entire bounded history and selected suffix. Missing target after committed A5 is inconsistency; do not create an empty target. A genuine target-version conflict holds/requires replan, never silently overwrites or silently substitutes a new expected version.
4. Reclassify using this target with the same explicit asOf. Acquire one complete `lockImportIdentities` set for all candidate economics, prerequisite economic identities/target IDs and selected deliveries, using existing helper key conventions and actual advisory-lock ordering. This covers absent as well as existing records. Do not acquire keys incrementally; if selection/closure changes, abort and prepare again. Capture can wait on delivery keys but apply never reaches back for a capture checkpoint/global stream lock.
5. Validate globally locked delivery canonical content/position, financial records and original receipt associations. Recheck exact unit/plan equality and grants; project with existing parent/finance helpers and validate expected balance at that same asOf. No bootstrap `ensure_*` operation. Parent financial rows, snapshot and metadata must agree; an unexplained record/receipt mismatch is storage failure, not an external correction to absorb.
6. Lock application outcome/progress heads in stable `(sourceRef,manifestHash,streamId,sequence,eventId)` order after identity locks; account serialization prevents same-account races. Verify expected prior frontier and every covered position from authoritative stored outcomes, exactly as bound by W'. A source-wide hold writer, if later introduced, must have a separately reviewed compatible fence; this proposal does not invent that writer or a commit-time capture fence.
7. For nonempty apply, insert only new records; append a validated snapshot at checked target version+1 and plan.asOf; CAS the parent target pointer; append receipt, exact plan and lineage; write original economic/delivery associations, unit membership, event outcomes and eligible progress. For all-replay bookkeeping, omit all monetary/snapshot writes and use validated originals. The head/epoch lock is still held and checked for new bookkeeping: F5 and PRD §§10/16 already require active authority for acknowledging a newly delivered event; old economics do not make that mutation read-only recovery.
8. Publish safe runtime activity/counter last in the same transaction (`batch.applied` for the new nonempty unit; replay bookkeeping only under a reviewed deduplicated activity binding). Assert active epoch remains held immediately before commit. Commit, then return/emit. No outside callback between final fence and commit may introduce external I/O or release/recycle the client.

Order: **parent-scope → authority head → target → complete global identity set → application outcomes/progress → activity counter**. Status uses its accepted prefix; capture remains checkpoint/global-stream/delivery only and never acquires account authority. First import keeps its own existing scope/import-key/target/identity order. Application does not lock status-command rows or modify authority status.

Use existing bounded whole-transaction retries for 40001/40P01 only, at most three attempts. Every attempt rereads head/target/outcomes and obtains fresh lock tokens. A retry may reuse this attempt's prepared immutable input/asOf/semantic observation only with all locked checks repeated; it cannot treat a stale epoch/target as a SQL retry. A failed attempt leaves no financial record, snapshot, receipt, outcome, frontier or activity. A lost response after commit recovers the stored receipt; exact recovery performs no new commit effects.

Revoke/pause barriers follow accepted authority rules: if revoke wins the head, prepared old-epoch new apply cannot commit; if apply wins and commits first, revoke waits, then blocks subsequent new work while retaining the earlier receipt. Pause followed by resume changes epoch, so pre-pause plans cannot silently match renewed authority. This requires actual financial writer tests; existing head-only tests do not prove it.

## 6. Application progress and smallest first increment

Application progress is separate from the capture vector. Initialize a new application head only from the exact original activation's manifest/baseline cursors, preserving each stream independently. Label that prefix approved baseline coverage, not newly applied events. Do not adopt another lane's latest capture cursor or count baseline members as ongoing imports. History without its progress head is corruption, not permission to reset to baseline.

A safely specified advancement exists for a contiguous financial prefix whose every position is committed as new/coalesced application or validated replay with an authoritative receipt. Its frontier cannot exceed durable inbox membership. New financial records, receipt, delivery outcomes and this advancement share the same runtime transaction; applied events after any unresolved gap cannot move the contiguous frontier across it. Captured high water and application position remain separate. No “fully reconciled” claim follows while gaps or unknown coverage remain.

**Recommended first independently testable increment:** internal, unmounted transaction service for one committed API-only lane, one active enrolled customer, one selected financial stream's complete currently captured unapplied suffix, one complete accepted dependency group and at most the existing event limit. The §5 coverage predicate mechanically requires every other declared stream to remain at its exact baseline and verifies the complete bounded source-global history at W'; their application frontiers remain unchanged. A happy-path fixture exercises this predicate but cannot replace the SQL evidence. Prerequisites already exist in the parent or belong to that selected suffix. New, mixed replay/new, coalesced and all-replay financial units are included because omitting these would leave the receipt boundary unproven.

The service resolves actual stored history/suffix membership and prerequisites; test-owned preparation is not a bypass of inbox, authority or money checks. Reject unsupported coverage (semantic-only position, another account's position, unknown raw identity, prior held/quarantined gap, noncontiguous unit, multi-group aggregate, missing dependency or unbounded blocker scan) without financial/progress writes. Such rejection is a limited primitive outcome, not an automatic source pause, successful resolution or final production quarantine policy. Captured input remains durable for later work. No caller can label arbitrary positions skipped/resolved to satisfy the precondition. The lifetime 1,000 post-baseline-history bound, single-lane restriction and rejection of any post-baseline nonselected-stream input are intentional scope limits; this is not a production long-running scheduler.

This increment is useful without a runner: real PostgreSQL integration drives accepted capture and genuine A5, then calls the internal writer with exact immutable selections. It proves atomic persistence/recovery and authority fencing. It does not prove dependency release, independent-customer scheduling, general progress closure or an end-to-end connected product. Expanded selection must wait for its own reviewed contract; failure to support a case is reported as unavailable/held, never silently converted into successful progress.

## 7. Required later verification and sequencing

No code or test was authored or run for this document. A later plan must reserve exact paths/DDL and define strict persistence/interface shapes, bounded safe failures and tests before implementation. The following assertions are required for the first increment, not claims of a pass:

- Genuine A5 plus accepted capture: a fresh financial prefix changes parent version once, has exact expected operation IDs and balances, and commits receipt/origin associations/membership/outcomes/frontier/activity together. Preserve all original approval and snapshot bytes. No control writes or model dependency.
- Mixed example in §4: E1 maps to R0's original P, R1 acknowledges E1/E2, only A is inserted, and initial receipt/association stay byte-identical. Cover original ongoing receipts as well as original initial receipts; multiple original receipts in an all-replay unit remain distinct.
- Coalesced new economics and exact repeated deliveries: one financial record/effect, correct original receipt pointers, one outcome per global delivery and distinct unit event membership. Different content/observedAt at occupied delivery, changed economics/effective time or foreign-account global economic collision rejects atomically.
- All replay at active authority: no new receipt/snapshot/version; new delivery association and contiguous progress commit together. Exact plan retry after later apply, pause/revoke, restart or source outage returns the old receipt byte-identically and changes nothing. Missing/corrupt/ambiguous original receipt does not fabricate success.
- Semantic/schema mismatch, wrong scope/pins/epoch, no grant, unsupported operation, target mismatch, invalid dependency group, limits and unsupported coverage leave target/outcomes/frontier unchanged. A replay-equivalent item inside a held group stays held.
- `coverage_blocker_outside_selection`: capture a governing semantic event in a nonselected stream before preparation and separately between preparation and W'; both fail without monetary/outcome/progress changes even when the current-semantics endpoint reports approved equality. Also cover change-then-return history, source-wide missing-seller input, an extra lane/undeclared stream and an incident; none is hidden by selected financial success.
- `coverage_changed_before_locked_cut`: prepare W, commit a valid extra financial page before W', then prove the old attempt rejects instead of silently enlarging its unit. Fresh preparation selects the entire suffix and still requires one complete accepted group. Test missing page/inbox/delivery membership, C/B disagreement, 1,001 retained events and truncated bounded query results; no omission becomes coverage.
- `capture_after_locked_cut`: barrier after W' while apply holds authority/target, commit later capture, then let apply finish. Assert only W' events/outcomes/frontier are acknowledged; the later rows remain durable and outside that receipt. A subsequent new-work attempt sees a new witness and rejects if the later page contains unsupported semantic/source-blocking history. This documents the cut limitation rather than claiming a commit-time capture fence.
- Barrier-controlled crash/failure after record, snapshot, receipt, association, outcome, progress and activity insertion proves full rollback at each boundary; lost response after commit proves recovery. Trigger failures are preferable to sleeps. Application activity/counter cannot outlive rolled-back records.
- Two writers on the same group produce one receipt/effect/frontier change; cross-account global identity collision serializes. Concurrent capture commits independently without a lock inversion. Real SQL serialization/deadlock retry reacquires authority and observes intervening revoke.
- Prepared apply versus revoke and pause/resume exercises both lock winners with real PostgreSQL barriers. Old epoch never commits after status wins; earlier committed receipts remain readable. A lock token reused across transactions/pool reuse is never accepted as execution evidence by the service.
- Unallocated payment leaves invoice balance unchanged; explicit allocation changes it; supported full reversal preserves original funding/allocation rows and reconstructs balance at its effective instant. Backdated fresh input changes latest reconstruction while original snapshotHash reads remain exact. Existing independent finance expectations must not be changed to fit implementation.
- Additive SQL constraints/FKs/privileges, origin exclusivity across initial/ongoing domains, canonical corruption, retained history and safe-integer version exhaustion fail closed. Runtime001–004 hashes and control catalog remain unchanged.

Sequence after repaired design review: retain accepted classifier `ec91a4b`; settle first-increment contract and ownership; reserve additive storage; write meaningful failing transaction tests; implement minimal writer using existing primitives; run typecheck, focused unit and isolated PostgreSQL suites under the assigned DB lease, including parent/activation/capture/current-authority regressions; obtain fresh independent exact-candidate review. Only then consider separately scoped scheduling/progress expansion. No existing unavailable V5/V6 runner, fixture-only proof or upstream CI status establishes final V5/V6, live two-company AI-off proof or joint acceptance.

## 8. Remaining resolution authority and deferred technical work

The one genuine product-policy boundary left for a general scheduler is **new authority to treat work as explicitly resolved**. PRD §11 already requires separate capture, per-event outcomes, contiguous applied/explicitly resolved progress, visible quarantine gaps and independent known-customer continuation. F1 forbids invented scope, and changed governing terms/unknown customers require the specified review/enrollment. The exact question, only when extending beyond this prefix primitive, is: which decisions may make foreign-customer, unchanged semantic or unknown-account positions terminal for a selected customer's frontier, who is authorized to make them, and which source-wide unresolved coverage must remain visible?
