## Findings and smallest fixes

### 1. P2 — Final plan failure has two incompatible output contracts

Design line 71 requires all tentatively accepted financial items to become `held` under the existing final hold. That implies a `classified` result, with its item/group invariants updated. Design lines 58 and 149 instead provide `plan_invalid` and require fatal plan failures to return `not_classified`. A consumer cannot rely on exhaustive classified detail or on whole-request rejection consistently, and an implementer must choose between contradictory verification requirements.

The actual branch is `packages/compiler/src/plan-batch.ts:361–365`: after all group processing, a `FinanceError` in `resultPlan` returns no plans, preserves earlier holds, and appends a hold over all accepted events. No per-item success may survive this branch, but either additive representation can preserve the legacy outcome.

**Smallest recommended correction:** keep the document's conservative whole-request approach. Replace the final-failure sentence at line 71 with: “If final `resultPlan` throws a caught `FinanceError`, return `not_classified` with reason `plan_invalid`, reference the appended final hold in `holdIndexes`, retain the exact existing `outcome`, and emit no item/group acceptance claims.” Add that case explicitly to line 58. This matches line 149 without introducing partial-result states or changing money behavior. Alternatively, classified-held is technically possible, but would require removing `plan_invalid`, narrowing line 149, and specifying the downgrade of every accepted group as well as its members.

### 2. P2 — Specify parsed canonical delivery equality to preserve existing normalization

Design lines 28, 60, and 69 use original/identical canonical event bytes to define repeated occurrences without saying whether these are the original input objects or the schema-parsed event objects. This matters for exact compatibility and exhaustive classification.

`packages/compiler/src/plan-batch.ts:229–241` validates canonical input, parses it through `SourceEventSchema`, checks the hash of that parsed event, then deduplicates by delivery key. `packages/contracts/src/source.ts:10–14` uses `IsoInstantSchema`; `packages/contracts/src/common.ts:45–54` normalizes a valid `...00Z` instant to `...00.000Z`. Two occurrences differing only by this accepted envelope spelling, both carrying the hash of the normalized event, are accepted and deduplicated by today's planner even though their pre-parse canonical JSON differs. Requiring raw-input byte equality would leave this existing accepted case without a valid final disposition or tempt a new conflict rule.

**Smallest correction:** state that representative/repeat metadata uses the **same parsed, hash-validated event representation used by `parseEvents`**, including existing timestamp normalization; retain original occurrence indexes separately. Do not add a raw-input equality guard to the planner. Add a future compatibility case for equivalent accepted timestamp spellings and a separate case proving that a changed observation instant still conflicts. This does not relax F1 retransmission identity; F1 already specifies normalized `IsoInstant` representation. It also does not change the later runtime capture contract's immutable-content checks.

## Output location and schema recommendation

As a technical proposal, the smallest compatible placement is compiler-owned output types and the additive function exposed through the existing `@eapr/compiler/plan-batch` subpath (`packages/compiler/package.json` already maps that surface). Keep the trace evaluator private and the existing `planBatch` return type untouched. An additional root contracts export or transport schema is not needed merely for an in-process pure companion; if a later reviewed consumer requires a serialized boundary, the integrator can place strict Zod schemas under shared-contract ownership then. This recommends a boundary, not a path reservation or permission to implement.

The proposed discriminated result is otherwise adequately scoped for planning after the two corrections. All index/version fields should use existing nonnegative safe-integer conventions in any executable schema; the cross-reference/exhaustiveness invariants already documented are essential. Do not add a separate scheduler-status vocabulary, receipt schema, connection head, or authority input. Preserve protected evaluator build-closure and coverage maintenance for any eventual compiler extraction/export change, as the candidate already requires.
