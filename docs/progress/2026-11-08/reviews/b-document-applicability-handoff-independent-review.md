## Sound boundaries

- The accepted guided-discovery handoff's source reader rules explicitly authorize the narrow anchored A/B agreement grammar, manifest-as-of checks, and recognized agreement/directory conflict detection. `source-coverage.ts` implements those observations. Extracting that grammar into an internal primitive is justified; treating its display response as authority is not.
- `discovery-reads.ts:readDiscoveryCaptureContents` is the appropriate producer seam. It calls `inspectBaseline` with the registered source, verifies expected citations and capture membership, and rechecks selected rows after blob I/O. `dossier.ts:inspectBaseline` checks original length/hash and reproduces extraction through `verifyExtraction`. The feared missing byte-reproduction prerequisite is not evident in the inspected code.
- A one-page, full-range captured agreement can supply a derived seller/account association while file `excerptCoverage.identities` remains empty. Association is not complete exposure coverage, authenticity, signature verification, financial support, parent identity, approval, or activation authority. Account-only readers and callers remain denied. Explicit printed seller plus exact captured event tuple, rather than names or document-ID conventions, is the correct boundary.
- Full-capture recognized conflict inspection, including the recognized first page of an otherwise unsupported multipage document, prevents hiding an identity conflict merely by adding pages. Unknown documents and ambiguous requested citations stay unresolved. No new amendment selection, latest-contract rule, or unsupported financial inference is introduced.
- C1 currently relies exclusively on account-filtered event citations in `construction-evidence.ts`. C2's `proposal-evidence.ts` has the same limitation. A private trusted adapter can extend that association check without changing public model inputs, event provenance, or model-authored profile content.
- The mandatory installed adapter, exact binding/facts equality, explicit complete partition of requested IDs, transaction fences, and sticky historical blocker preservation are appropriate. Fresh runs are necessary for the proposed happy path when earlier runs already acquired sticky applicability origins.

## Required corrections and exact integration details

1. **Pause is not automatic cancellation of already claimed work.** The final consumer verification bullet currently groups pause with revocation/owner replacement/stale state and requires that it “cannot settle proof.” The accepted orchestration proposal's pause paragraph explicitly permits already claimed work to settle; it prohibits new claims after pause commits. Replace the blanket requirement with tests for both orderings: pause before claim prevents preparation/effect; pause after claim retains the existing claimed-step settlement semantics and all current authority/generation/capture/revision checks. Do not change lifecycle behavior in this slice. Revocation, owner replacement, and stale proposal/finding revisions still fail under their existing fences.

2. **Batch C1 as well as C2.** “50 per call is sufficient for C1” is incorrect for the combined citation set. `discovery-construction-tools.ts` permits 50 main refs and up to ten alternatives, each with up to 50 refs; `construction-evidence.ts` unions all of them. A valid finding can exceed 50 distinct IDs. Keep the private producer cap if desired, but require the shared consumer helper to sort, deduplicate, and split every larger set, including C1 alternatives, with identical binding/facts checks for every batch. Add a C1 case with more than 50 distinct refs across main/alternative citations, and a case where an unresolved or malformed result in a later batch blocks the whole finding. Never truncate the union or change the public finding limit.

3. **Freeze the C2 requirement matrix after C2 acceptance.** The actual candidate module is `packages/discovery/src/proposal-evidence.ts`; it exports `prepareProposalEvidence`, `proposalCitationIds`, `profileSubjects`, and `tupleKey`. It distinguishes all readable refs (including retained refs) from profile-bound refs and parent-account lookup entries. Its `boundRefs` currently resolves across the validated profile tuple set; lookup-entry refs are checked for their exact source-account entry. The handoff should name this module and require preserving those exact per-field constraints while sharing only the citation-to-tuple association helper with C1. Do not silently change profile-wide citation requirements into “every reference must apply to every alias,” or relax exact lookup entry checks into “some profile account matches.” Add an alias/multiple-source-account test that distinguishes those cases. If the final accepted C2 shape differs, root must update the matrix before consumer dispatch. This is an explicit sequencing dependency, not a reason to postpone the independent producer.

## Verification sufficiency and limits

The proposed producer tests meaningfully cover supported formats, changed public inputs, seller collisions, conflicts, exact citation binding, immutable older captures, original/extraction corruption, read-only behavior, and account-only disclosure denial. The specified integration and regression suites are appropriate partial evidence. Add the batching and pause-order tests above and retain malicious adapter-result checks on the shared consumer seam.

The design does not guarantee compiled/eligible proposals or successful V4 acceptance. Its financial/name mutation test must assert that association supplies no value-verification result; it must not invent a new semantic verifier merely to make a mutation fail here. Independent construction, financial/bootstrap verification, parent-scope capability, and any governing-contract interpretation remain separate gates. Existing unknown/ambiguous document coverage remains blocked, and no account-only PDF privilege is granted.

After these handoff corrections, the source producer is suitable for Sol implementation followed by exact-candidate review. Consumer integration remains serialized behind accepted C2 and an explicit final private-interface transition. No test pass or implementation acceptance is claimed by this review.
