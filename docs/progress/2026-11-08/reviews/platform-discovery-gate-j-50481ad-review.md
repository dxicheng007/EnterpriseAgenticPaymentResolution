## New correction regression

The uncertain path creates an `ok:true` result at `:1421–1423` and still calls `resolveStep` at `:1482`; that helper marks the current step succeeded (`:746–749`).

A replacement can observe an originally running job whose original launcher ownership is unknown, then have the proposal/assessment invalidated between that observation and settlement (the existing `afterVerificationEnqueue` barrier permits exactly that ordering). The changed code now skips the invalidation check and publishes current success. The original code checked it. This is distinct from merely allowing a historical authorized observation: it updates the current tool step/transcript and task revision. Keep uncertainty as separately authorized historical observation; do not bypass current-success validation. Add the uncertain-running variant of the existing stale-assessment-after-enqueue test, plus pause/capture variants. This finding is source-derived, not an executed reproduction.
