**Specification verdict: changes requested, bounded to the recovery/admission distinction below.** The overall design preserves the specified attested financial execution and trusted-scope interim rule. It correctly supersedes the outdated legacy-jobs and bootstrap-unavailable statements with current accepted A1 behavior; no new product policy is needed for that correction.

**Engineering-quality verdict: changes requested before implementation dispatch.** Atomic reservation on the actual owner connection is viable; the gate contract and its acceptance sequence need a concrete resolution. No broad redesign is indicated.

## Blocking corrections

1. **Separate historical request recovery from new/current-subject admission (draft lines 43, 55–59, 66–72).** Step 1 requires current exact compiled subject, task revision/dispatch/generation and batch preflight before mapping lookup. That is appropriate for a new admission but cannot be applied unchanged to recovery of an already-admitted old-generation step after proposal revision or tool settlement advanced task revision. The draft simultaneously promises same-key recovery in every state and historical visibility after interrupted settlement. Current `supervisor.ts:loadStep` distinguishes terminal replay from runnable step contexts, and replacement reconciliation changes the old step's state/generation; a generic “repeat all checks” gate is insufficient. Specify distinct gate operations/results for (a) admitting an absent mapping, (b) authorized immutable historical lookup, and (c) queued execution recovery. Historical lookup must authenticate current run/source/account authority and the persisted original step/request association, compare against the original immutable candidate subject, and avoid demanding that historical candidate still be the current proposal head. It must never relink stale verification as current success. Explicitly state when queued recovery may execute while paused, versus merely inspect; apply the already-admitted-work rule without creating a new admission. Add a barrier case: reserve → change proposal/finding assessment or advance task revision → restart → recover original job as historical with no new budget or current link.

2. **Resolve the producer/consumer acceptance dependency and publish the actual gate type (draft lines 43, 76–82, acceptance section).** Producer acceptance requires integration tests using the real supervisor `transact`, while the owner gate is assigned only to the Discovery consumer after producer acceptance. Today `transact` is private; public/test-hook surfaces do not expose a general owner-transaction callback. The producer's assigned paths do not include the required supervisor seam. Root should explicitly reserve a narrow Discovery-owned owner-gate prerequisite (and precise tests/paths), or distinguish a producer-only SQL acceptance gate from the later mandatory joint owner-fencing gate. Do not label a test-created advisory-lock transaction as proof of the actual lifecycle implementation. Publish a minimal typed gate contract before dispatch, including immutable persisted request binding, callback lifetime, commit outcome and loss/denial results. Current `transact` returns `undefined` on owner loss, including possibly after COMMIT; that must not become an invented successful observation or scheduling from unconfirmed local state. Recovery must use the mapping. This is an engineering ownership/sequence correction, not a request for additional user permission.

## Implementation requirements worth making explicit

- `registry.start` commits running state and then performs external candidate revalidation before returning. A competing claimant and a claimant whose post-commit revalidation fails currently both throw. The new claim primitive should return an explicit nonwinner/claimed result before post-claim I/O; only a positively known claimant can fail a job after its own validation/execution error. Connection/COMMIT uncertainty must remain non-success without guessing ownership. Preserve reviewer behavior separately. The draft already states the right invariant; spelling out this split prevents a superficially refactored `start` from retaining the existing race.
- Retaining an uncertain job as running is conservative and needs no timeout policy. However, V4d requires safe failed/interrupted diagnostics when uncertain launcher recovery is unsupported. Define where the Discovery interrupted/uncertain diagnostic is exposed without changing the financial job to failed or forging completion. Ordinary `{state:'running', diagnostics:[]}` alone does not explain a restart-stranded job. This can be a lifecycle diagnostic; no financial retry policy is required.
- The proposed mapping/FK approach is implementable additively: control006 already has `(job_id,request_hash)` uniqueness; control004 needs an additional UNIQUE constraint for a composite step/run/task foreign key if that is the chosen enforcement. Preserve applied SQL. Explicitly reserve migration/catalog/test-fixture changes before implementation, as the draft requests.
- Keep canonical registered spec equality explicit: current `requireFinancialCandidate` compares artifact/manifest/snapshot/profiles but not the supplied `spec`. The proposed full candidate subject must compare the input spec with the authoritative registry result as well; do not merely hash whatever input spec accompanied a valid artifact.

## Positive findings and scope

The design correctly keeps preparation external, budget/job/reservation/key/Discovery claim atomic, execution after commit, max-three run/account budget unchanged, immutable first pins/build preserved on replay, competing starts unable to fail the winner, and running uncertainty non-relaunchable. It preserves exact saved-request validation and atomic report/attestation completion, denies proposal-created capability, separates bootstrap/activation readiness, and calls for real app-role permissions and source-build closure regression evidence.

Material product gaps remain only in explicitly deferred areas: generated-account capability (Blocker B), autonomous abandoned-running terminalization/retry, repair/finish semantics, and live provider configuration. They do not prevent the trusted-scope producer once the bounded engineering corrections above are resolved. No implementation or acceptance of this draft, migration number, live keys, new capability, or V4 completion is implied by this review.
