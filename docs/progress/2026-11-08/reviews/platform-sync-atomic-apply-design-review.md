## Finding

### P2 — Specify the bounded coverage proof, not merely the fixture condition

Candidate lines 72–74, 83, 99–103, and 115.

The design requires captured source-wide governing blockers or selected-customer drift to prevent new application. It also excludes prior gaps and says other streams are pinned/checked, while describing their lack of new unresolved input as a test-fixture property. The transaction sequence verifies selected deliveries and application frontiers, but does not identify the authoritative coverage set/cut inspected for the other streams, how a bounded scan proves that it is complete, or what happens when that coverage changes during preparation or application. Capture may continue independently, and the document intentionally forbids acquiring capture checkpoint/global-stream locks. Existing capture stores immutable pages/positions and mutable checkpoints; it does not publish an application hold/clearance fence. The current authority head likewise contains no source-hold state.

A successful classification of a selected financial prefix cannot certify absence of a captured blocker outside that prefix. Nor can the current semantics endpoint prove absence of a previously captured sticky governing change: its equality check supplies the current revision observation, not a complete durable hold history. Empty other streams in a happy-path fixture demonstrate only that fixture.

Before the later implementation plan, state the first increment's exact coverage predicate and evidence: which actual stored streams/positions/history it checks, the bounds and explicit failure when completeness cannot be established, where the checks occur relative to the transaction, and the intended concurrency/observation boundary. Add named cases for a blocker already present outside the selected prefix and for capture changing relevant coverage between preparation and the locked check. Preserve the accepted distinction between declared event dependencies and source-observation limits; do not claim atomic external source/runtime observation. If a stronger source-wide hold fence is necessary, reserve and review it separately instead of implicitly introducing it through the apply writer. Alternatively narrow the supported internal service contract concretely enough that unsupported coverage is mechanically rejected. No new automatic resolve/skip authority is needed.

This finding concerns an omitted proof contract, not a demonstrated defect in implemented code. The design already requires failure on unavailable coverage; completing that requirement is sufficient to avoid turning the first increment into a general scheduler.

## Confirmed design conclusions

1. **Economic origin and acknowledgment membership are distinct and correct.** F5 explicitly requires a new delivery replaying old economics to associate with the original receipt, while a mixed receipt records all acknowledged event IDs. Candidate lines 48–54 satisfy both. R1 may acknowledge E1 while E1/P retain R0 as their effect origin. Coalesced new deliveries share the one new operation's receipt. Original records, source event/version, initial receipt, and initial associations remain unchanged. `targetRecordIds` as ordered financial operation IDs agrees with the accepted parent storage guide and existing initial receipt validation.

2. **All-replay work must remain separate from a new monetary receipt.** F5 expressly rejects an invented zero-effect receipt and restricts `applyBatch` to a nonempty mutation group or exact existing-plan replay. Candidate line 56 obeys this; a later internal bookkeeping interface may return multiple original associations. It still needs strict input/result, repeat/restart behavior, and activity deduplication in the implementation plan. Those are technical contract tasks, not missing money policy.

3. **Receipt recovery must precede new-work gates.** Candidate lines 58–60 correctly preserve byte-identical committed results after later target changes, pause/revoke, or source outage, without reclassification against today's target or new progress/activity effects. Canonical request/plan binding and the immutable scoped association are essential. The concrete request binding, including handling of expected epoch on recovery, should be unambiguous in the later API definition; a hash alone remains neither authorization nor equality proof.

4. **Atomicity and account authority ordering are sound.** Parent-scope → current-authority head → target → one complete global identity set → application outcomes/progress → activity matches the accepted current-authority prefix and existing first-import/capture separation. The parent helper orders actual advisory lock IDs; it is not sufficient to acquire textual keys incrementally. Complete identity locking covers absent records as well as existing records. Same-account serialization, global parent economic uniqueness, canonical delivery checks including observedAt, and the current head retained through commit supply complementary protections.

5. **The existing token mechanisms do not detect transaction lifetime.** `lockCurrentAuthority` and `lockImportIdentities` bind tokens to a client in WeakMaps. `withTransaction` reacquires a client and reruns the callback on bounded 40001/40P01 retries. Candidate lines 79, 89, and 116 correctly require fresh tokens and service-owned transaction lifetime rather than treating a reused client/token as evidence that a lock is held. Status-prefix tests cannot substitute for the proposed real financial apply/revoke barriers.

6. **Additive persistence is required.** Runtime002's economic/delivery/lineage foreign keys reference initial imports, and the initial import/receipt is explicitly epoch 1. They cannot simply be reused for ongoing receipts. Candidate lines 64–68 correctly require typed initial/ongoing origins, enforced scope/record references, retained history, and proof of origin exclusivity across domains. A union read alone cannot enforce that exclusivity. The precise constraints/triggers or shared ownership relation remain a DDL design obligation; this document reserves none.

7. **Receipt boundaries cannot be inferred from classifier group indexes.** The inspected pre-classification planner combines accepted groups into one plan and omits all-replay plans. Candidate line 42 correctly requires one complete independently replanned group for the first nonempty unit and forbids slicing an existing plan's operations/eventIds/lineage. Classifier labels remain recomputation metadata, never global receipt lookup, authority, or scheduler clearance.

8. **The verification scope is appropriately modest.** Required rollback stages, original and ongoing replay origins, coalescence, changed delivery content, cross-account collision, target/version exhaustion, active epoch races, and historical snapshot preservation are meaningful. No test was run for this review, and the described future checks are not present evidence of a passing writer. Internal capture and current-authority services remain unmounted; accepted implementation boundaries do not establish a trusted production reviewer adapter or a production apply route.
