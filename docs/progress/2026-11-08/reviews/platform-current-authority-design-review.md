## Findings and smallest correction

**C1 — Make lazy initialization's retention assumption explicit (candidate lines 40, 138–147).** The intended head is durable current authority, yet the fallback sentence unconditionally projects active/epoch1 when it is absent. The proposed immutable command log and head/grant FKs already provide the ingredients to distinguish first use from inconsistent storage. Spell out their deletion behavior so a later migration or repository implementation cannot interpret the head as a disposable cache.

Smallest addition:

> A materialized authority head is never deleted or reset. The runtime application role receives SELECT/INSERT and column-limited UPDATE(status, epoch, changedAt), with no DELETE/TRUNCATE; command-to-head/grant foreign keys do not cascade deletion. If command history exists for the committed identity but its head is absent, reads and mutations return AUTHORITY_STORAGE_INVALID instead of projecting or recreating epoch1. Check absence/history in the same read snapshot or scope-locked transaction. Initial projection/materialization is permitted only when no prior status command exists.

Add one role-permission/FK assertion and one missing-head-with-history corruption case to the already proposed storage scenarios. Existing history FKs may make the latter unreachable through ordinary application SQL; it still describes the decoder's fail-closed contract. This is a technical clarification of immutable authority, not evidence of a currently implemented vulnerability and not a reason to introduce an event-sourced reconstruction subsystem.

## Basis for acceptance

- **Original authority remains historical.** `packages/parent/src/activation-store.ts` validates the committed bundle and canonical imports, loads the approved historical snapshot, and explicitly requires activation active/epoch1. Runtime002 makes imports append-only and unique per account. `ActivationStateV1Schema` pairs the original activation and initial receipt with equal epoch. A separate mutable head avoids corrupting these invariants; it must never replace the stored activation in the existing read DTO. Looking up the exact committed scope/activation/bundle is stronger and more appropriate than registry or capture-lane presence.
- **The narrow read is consistent with deferred ConnectionState.** A committed-identity API returning 404 for no grant does not claim to implement the list's inactive-account representation. The readiness document's tentative null/inactive recommendation need not be imported into this narrower DTO. Read-only REPEATABLE READ is the straightforward implementation using existing `readStoredActivation`, because its decoder performs additional historical-snapshot reads; do not put independent pool queries under a nominally consistent read.
- **Epoch and lock protocol satisfy the specified race.** PRD §§10 and local persistence guidance, shared contracts line 155, and freeze F5 require one activation lock held through commit. The proposed scope-advisory → head prefix serializes absent-head initialization and both status and future application; it is compatible with A5's existing scope → import-key → target ordering because status takes neither target nor import-key locks. Incrementing each actual transition prevents pre-pause work from matching resumed authority. Expected-epoch checks on no-ops, checked increments and immutable retries remove important ambiguities. The future writer still must demonstrate that it actually takes the shared head lock and checks active/epoch before committing.
- **Reviewer provenance is represented honestly.** The existing local-session authorizer obtains server-managed reviewer/session and enforces mutation origin/CSRF. The worker's private service token authenticates the control channel. The proposal correctly treats forwarded reviewer data as a trusted-control assertion rather than cryptographic proof of a human action, and makes an opaque admission object merely an in-process enforcement mechanism. Full command/account/source binding, fresh admission on every retry and rejection of plain actor JSON are appropriate. Deferring the mint/ingress adapter and permitting repository-only work until it is reviewed prevents a service-only implementation from silently creating a public authority port.
- **Retry binding is coherent.** Account-scoped status keys are safe under F1's globally unique canonical account IDs and are separate from A5's global activation keys. Binding exact command and reviewerId while preserving original sessionId in immutable internal audit permits the same reviewer to recover after session replacement without accepting another reviewer's command. Historical result replay preceding current epoch/preflight checks does not reinstate authority because the response is explicitly historical and side-effect free.
- **Resume uses the actual producer's guarantees.** Candidate equality rules match `validateSemantics`: exact source, no governing wildcard, all selected seller/source-account keys present in both manifest and observation, equality to the pinned profile revision, unrelated customer revisions ignored. `createSourceSemanticsClient` supplies the stated loopback allowlist, source token, timeout, redirect rejection and response cap. Observations occur outside runtime transactions. Rechecking committed association after observation failure matches A5's lost-response recovery pattern. No TTL or revision ordering is invented; the v2 addendum explicitly treats checkedAt as observation without TTL. The candidate accurately limits this to declared semantics and preserves future event dependencies/schema/document coverage as separate obligations.
- **Status control does not acquire new financial powers.** Pause/revoke depend on genuine saved authority, not contemporary activation policy or evaluator files. Resume cannot change pins, clear data holds, reenroll a revoked account, or mutate parent records. This fits the PRD's bounded standing approval and leaves existing per-account immutable import constraints intact.
- **Activity and transaction mechanics fit existing code.** `withTransaction` uses one checked-out client, at most three whole attempts for 40001/40P01, and bounded jitter. `publishActivity` retains the proposed status and three hash fields; `connection.paused`, `connection.revoked`, and `system.status` are accepted types. Activity is last and atomic with head/log changes. Avoiding activity on retry/no-op preserves a clear audit distinction while the immutable command log records successful no-ops.

## Remaining gates

The admission adapter needs its own exact transport, authorization and capability-lifecycle review before any mutation surface is mounted. The financial writer needs its own current-head/semantic dependency integration and apply-versus-revoke/pause/resume barrier evidence. Source schema/document notification completeness remains independently bounded. These are already stated integration dependencies, not missing requirements that need a generic user clarification.

The candidate's epoch/no-op rules, account-scoped key namespace, session retry policy, narrow read/error shapes and observation audit fields are reasonable technical choices within the existing specification. No source semantics, financial treatment, reenrollment or authority expansion was added by this review. Ownership and migration reservations remain with the coordinating owner after capture's shared files are released.
