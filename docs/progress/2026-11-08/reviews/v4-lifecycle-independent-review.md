## Required handoff clarifications

1. **Timeout must have an explicit durable transition and late-result rule.** Lines 39 and 66 correctly distinguish timeout from underlying Promise settlement, and lines 69–70 fence ownership-loss callbacks. But a timeout while the same owner remains healthy is only described as “may mark unknown/block”; the result-acceptance procedure at line 67 does not say whether that timed-out dispatch can subsequently accept its late valid result. Implementers could retain an unknown count while also adding known usage, execute its pending tools after a pause/resume, or count the same unknown again during ownership recovery. Specify one exact state machine: atomically mark the timed-out reserved dispatch interrupted with an idempotent unknown-accounting marker and persistent blocker; its late callback only settles/releases the process-wide permit and cannot publish accepted output or tools. Recovery recognizes that same marker and does not increment unknown usage again. If a different late-usage reconciliation policy is intended, spell it out separately without permitting side effects or replacement calls. Add a same-owner timeout → pause/resume → late success → owner replacement barrier test. Existing lines 78 and 80 test permit retention and owner loss separately, not this interaction.

2. **Make start-replay ordering unambiguous.** Line 64 first requires unconfigured start to return 503, then permits an existing idempotent run lookup when configuration disappears. The same line and line 52 bind identity to request/binding, while lines 41–43 require current authorization and capture validation. Explicitly distinguish new creation from replay: authenticate/current-authorize; look up actor/key and compare canonical request; replay the saved response for an authorized exact existing request without creating/scheduling work, even if no model is configured; require configured model plus validated exact capture only for new creation. Alternatively specify a deliberate 503-on-replay rule, but do not leave both outcomes implied. Never refresh a saved run to a latest/new binding. Add configuration-disappears replay and revoked-policy replay cases. This is idempotency/error-order clarification, not new customer authority.

## Small prerequisite dispatchable now

Dispatch the **source-owned read-only pinned capture validator** from lines 31 and 43 as a separate small change. Scope: `packages/sources/src/discovery-reads.ts`, minimal extraction/export in `dossier.ts` and `index.ts`, focused source/integration tests. Publish an exact typed result containing the immutable DiscoveryBinding, captured source-account subjects, and citation membership needed by lifecycle consumers; it carries no grants or candidate answers.

Reuse existing inspection/hashing rather than recapture: `dossier.ts:149–239` checks manifest members, stream consistency and original bytes; `aggregateHash` is at line 242. Do not assume calling `readDossier` alone validates the aggregate. Validate exact company/source/manifest, canonical hashes, full aggregate event/evidence membership, original blob availability and citation binding. Prove missing/corrupt/mixed captures fail with zero source/lifecycle/activity writes. Source tables are SELECT/INSERT-only to the app except mutable dossiers (`db/control/002_sources.sql:71–76`), supporting immutable member rechecks outside blob I/O; the validator must not rely solely on a dossier's mutable completion flag. Root/source owner should publish the exact return type and error adapter in this prerequisite's handoff.

After the two protocol clarifications, L1 is separately dispatchable with its existing narrow ownership. L2 follows L1 review plus this validator, the strict delegate schema approval/publication at line 91, and shared configured authority wiring at line 92. No need to wait for bootstrap, provider keys, findings, verification or UI to perform these bounded prerequisites.
