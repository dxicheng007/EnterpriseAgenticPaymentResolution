## Clarifications and smallest corrections

**C1 — State the repository lock-token lifetime explicitly (plan lines 131–142, 176–178, 185, 203).** The proposed WeakMap binds `LockedCurrentAuthority` to a `PoolClient`; synchronous `assertActiveAuthority` can validate that identity and cached state, but it cannot establish that PostgreSQL still holds the locks. The plan correctly requires a live caller-owned transaction and head lock, and acquires the lock within `withTransaction`, so its prescribed service flow is implementable. Make its exported repository contract as explicit as `packages/parent/AGENTS.md:9`: a client is not a transaction, and a token must never survive COMMIT/ROLLBACK into another attempt or pool checkout. Otherwise a future consumer could retain an old active token and reuse it on the same client after a revoke.

Smallest correction: add “Acquire a fresh `LockedCurrentAuthority` inside every `withTransaction` callback attempt. Never retain or reuse it after COMMIT/ROLLBACK, across retries, or across pool reuse; the same-client check is not proof of a live PostgreSQL lock.” Keep `assertActiveAuthority` synchronous if desired; no shared transaction refactor or new financial writer is needed. Add a meaningful service retry case that forces one supported transaction abort and proves a fresh head read/lock on the next attempt. Do not claim stale-token rejection as an enforced runtime property unless implementation adds actual lifetime enforcement.

**C2 — Put account authorization after extracting a validated account (plan lines 111, 117, 182).** Line 111 currently says to reject a forbidden account *before* parsing/detaching caller input, while the generic authorizer accepts only `request` and no account. This is a small sequencing ambiguity, not a reason to inspect mutable unvalidated nested properties. The rest of the plan correctly places required admission before any data exposure and freezes the request before later awaits.

Smallest correction: state the sequence as required authorizer → strict detached grants → strict detached command/identity → check parsed account grant → private committed-grant lookup → check its actual source grant. Malformed input from an authenticated caller can return400, valid forbidden account403. If account denial must precede other body validation, specify a minimal guarded account-envelope parse instead; that is not necessary to the accepted design. Keep all final authorizer checks outside SQL locks.

**C3 — Clarify occupied-key versus wrong-identity precedence (plan lines 129–144, 182, 200–201).** The accepted design distinguishes unknown/mismatched authority404 (design line36) from a different canonical command at an occupied `(accountId,key)`409 (design lines75,124). Plan step4 already requires changed identity to conflict. A snapshot implementation that immediately rejects the supplied activationId/bundleHash before inspecting the account-scoped command will instead return404 for that required test. This is resolvable within the proposed read port; it is not a request to weaken identity matching or authorization.

Smallest correction: explicitly require that, for an occupied account/key, the snapshot resolves and validates the persisted association and its genuine grant, checks the caller's account/actual-source grants, and reports a differing canonical command/reviewer binding as409. Apply wrong-identity404 when no occupied association exists (and for the narrow read). Keep storage-corruption checks before replay/conflict and never expose an association to a caller without its grants. Include separate tests for changed activationId, bundleHash and same-account scope at an occupied key versus an unused key. A private snapshot helper can use the persisted association's scope to call existing `readStoredActivation`; no public lookup or parent package change is required.

These are nonblocking plan clarifications because the accepted design and the plan's required tests already establish the intended behavior, and the prescribed service transaction flow need not reuse a token. They should be reflected before implementation to avoid divergent interpretations.

## Basis for acceptance

- **Admission is an explicit trust dependency.** The required generic authorizer has no permissive default; callers do not pass actor/grants as a public method argument. Private per-invocation token identity, detached/frozen input and grants, source binding, `finally` deletion, and the post-observation recheck provide a coherent internal lifecycle. Current `authorizeReviewer` returns server-managed reviewer/session and grants and checks origin/CSRF for mutation, but the plan correctly does not claim to implement or mount that adapter. Its final authorization recheck and same-session requirement prevent an observer wait from carrying a revoked test request into mutation/recovery. The stated short in-flight authorization assumption is honest; a WeakMap is not continuing session authority or cross-database atomicity.
- **Only genuine committed A5 grants count.** Existing `readStoredActivation` decodes canonical persisted request/reviewer/bundle/activation/receipt, validates bindings, and loads the historical approved snapshot using its passed client. It requires original activation active/epoch1. A separate current head preserves that historical representation and its initial receipt. The existing scoped import UNIQUE tuple supports the planned FKs without modifying applied migrations. Registry presence and source capture are not substitutes for authority.
- **Reads and retention are sound.** A read-only REPEATABLE READ transaction on one checked-out client covers the decoder's nested historical-snapshot read and current head/history/association. No-head-plus-history fails even for replay; first-use projection has no writes. App-role head DELETE/TRUNCATE denial, immutable columns, noncascading scoped FKs, immutable logs, and owner-only corruption fixtures address the accepted C1 correction. The migration's initial-state and transition triggers can be implemented using existing scalar projection helpers without treating a digest as authentication.
- **Status results are bounded and retry safe.** Exact command plus reviewerId binds the account-scoped key, while original sessionId remains immutable private audit. New-session retry is permitted only after fresh admission. Result/action/epoch/timestamp refinements reject impossible transitions; no-op preserves state and has its own audit time; checked increment fails at the safe maximum. Replay returns historical result rather than changing current state. Failed commands consume no key, and current policy/source availability cannot prevent pause/revoke/replay.
- **Resume matches actual APIs.** `selectedProfile` and `validateSemantics` are exported and can remain unchanged. The latter enforces exact source, no wildcard, selected account presence and pinned revision equality, while ignoring unrelated customers' revisions. Strict `SemanticPreflight` parsing and observation timestamps are compatible. Failure recovery rereads the association after fresh authorization; concurrent exact winner recovers, conflicting winner conflicts, and failed observation without a winner writes nothing. All awaited observation/authorization work stays outside runtime locks; pure semantic revalidation under the lock is safe. No TTL or comprehensive schema/document coverage is invented.
- **The fence has the correct limited claim.** Scope advisory lock → head is compatible with A5's scope → import key → target order. Status changes do not acquire target, economic, capture or application-progress locks. Checked epoch changes across pause/resume fence old prepared work. The tests exercise only the shared-lock prefix; future financial application must consume it and independently prove money/revoke races. This task performs no financial writes.
- **Verification and closure work are implementable.** Existing proof fixtures and `sync-capture.test.ts` provide genuine A/B A5 construction through `issueActivationProofs`, reviewer preparation and `createWorkerActivation`; the new suite can own a local helper without fixture refactoring. Real role/FK/corruption/barrier/rollback/restart checks are specified, including zero-change financial snapshots. Source observation can use the existing real source service behind injection. Both explicit evaluator contracts-source inventories exist, and adding the leaf plus mutation/recursive-closure assertions preserves protected pins without changing expected financial results. Parent-storage's privileged TRUNCATE list requires the two new dependent tables; no production cascade is justified.
