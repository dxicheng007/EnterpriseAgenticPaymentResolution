## Evidence and assessment

- **Committed authority and complete baseline:** Plan lines 99 and 124–130 resolve the immutable A5 import through the existing exported `readStoredActivation` rather than accepting caller evidence. `packages/parent/src/activation-store.ts:193` reads the scoped import; its decoder and `validateImport` check canonical digests, domain hashes, proof bindings, approved snapshot and activation baseline vector. The plan additionally verifies every baseline stream's sequence, membership and content preimage. This is necessary because A5 monetary persistence selects only plan deliveries (`packages/parent/src/activation-store.ts:318`), whereas the bundle contains the full captured source. `packages/sources/src/dossier.ts:50` supplies the precise stream-content preimage to reproduce with contracts helpers. Full baseline identities can be inserted into existing `runtime_deliveries` without inventing delivery outcomes: runtime002 defines and grants that table separately from `runtime_delivery_outcomes`.

- **Global identity and stale overlap:** Plan lines 111–113 and 135–138 preserve global delivery and position uniqueness, independent of account, connector version and capture lane. All identity comparisons precede stale/refetch/replay returns. Changed observedAt remains conflicting even with a recomputed event hash. A harmless longer stale page cannot splice in its suffix or advance progress. These requirements preserve frozen F1/F4 and the two scoped corrections accepted in `platform-sync-design-fix-review.md`. Empty responses are not persisted as page identities, so a later page at the same cursor remains capturable.

- **Lock ordering:** `packages/parent/src/persistence.ts:7` orders actual advisory lock IDs; `lockImportIdentities` at line 35 uses the established parent-delivery keys and orders the whole set once. Plan lines 128 and 135 use those helpers rather than assuming lexical key order equals acquisition order. Initialization takes lane, then all source-stream, then all baseline-delivery locks; capture takes its checkpoint, source-stream, then page-delivery locks. Initialization does not later lock existing checkpoints, and capture never acquires account/target/authority locks. This avoids the proposed reverse dependency and serializes different event IDs racing for one global position. A5 shares delivery locking but has no capture-checkpoint or source-stream dependency. The planned barrier tests at line 157 address the significant same-lane, cross-lane and initialization races.

- **Atomic page publication and safe errors:** Plan lines 134–145 keep page, global identities, inbox membership, cursor and `source.captured` activity in one checked-out-client transaction. `packages/storage/src/transaction.ts` supports that ownership and retries whole transactions only for its existing supported SQL states. The activity payload at line 139 uses only fields retained by `packages/storage/src/activity.ts`; no source document or financial result is published. Conflict/gap incidents persist only after rollback in their own transaction, deduplicate without changing first observation time, and failure to persist an incident becomes unavailable rather than a false durable success. SQL uniqueness remains a backstop, not an excuse to return replay after a conflicting race.

- **Storage and progress:** Plan lines 103–118 use runtime002's existing canonical encode/decode and projection conventions, immutable history triggers, global delivery table, and column-limited checkpoint updates. The parent package already exports the activation-store, persistence and snapshots subpaths, so no export-map broadening is necessary. Strict read validation and the one-statement progress snapshot at line 141 are sufficient for the declared capture-only counters and historical incident view. Baseline facts do not count as newly captured pages or records; capture progress makes no unsupported application, lag, money, or source-high-water claim.

- **Source/schema boundary:** Existing `packages/contracts/src/source.ts:28` defines contiguous ChangePage arithmetic, while `packages/sources/src/change-feed.ts:10` validates completeness and event hashes. The plan preserves that envelope and explicitly adds pinned page-size and resource checks. It correctly allows raw known-envelope events declaring a changed schema/semantic version to be durably captured without approving their interpretation. Noncontiguous/incomplete input must follow the plan's gap classification, while malformed input follows its 400 classification; this is implementable with structural validation before contiguous-page acceptance and does not require changing the source schema or source package. Whole-lane CSV rejection avoids claiming original-byte or batch-gap coverage that this internal service cannot establish.

- **Dependency closure and ownership:** The new barrel export changes the protected build dependency graph. The plan's Files and ownership paragraph explicitly reserves the two existing contracts source lists in `packages/evaluator/src/financial-attestation-build.ts:9` and `packages/evaluator/src/bootstrap-runner.ts:58`, plus their closure/mutation tests. The existing tests provide the required mechanisms: `financial-attestation-build.test.ts` checks imports/export targets and source mutations; `bootstrap-build.test.ts` checks recursive entrypoint closure and both evaluator/subject pins. Maintaining those lists is a narrowly justified build-binding edit, not a worker evaluator dependency or permission to change expected financial results.
