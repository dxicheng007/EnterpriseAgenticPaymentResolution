## Findings

### 1. [P1] Preserve tool calls and results in the provider transcript

Candidate `packages/discovery/src/live-model-transport.ts:33–35` sends only `kind:'text'`. Actual root `supervisor.ts:331–354` constructs `assistant_tool_calls` and `tool_result` messages after every tool batch. The adapter discards both, including retrieved evidence, delegation results and compile/replay feedback. Consequently the next invocation receives the original question and optional assistant prose without the results it needs to investigate or construct anything. This affects ordinary successful tool execution, not merely malformed inputs.

The discovery-shapes freeze requires an ordered transcript with exact call/result linkage; implementation-plan T4.1 explicitly requires visible tool results. Smallest correction: translate every message kind, preserve call order/native IDs and map each result's `toolStepId` to its preceding call's `providerToolCallId`. Send source content as tool-result data, preserving the supervisor's system-level untrusted-evidence instruction. Test a real-shaped two-batch transcript, including native-ID reuse across batches and distinct step IDs. Chat Completions uses assistant tool calls and tool messages referring to `tool_call_id` ([official API reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)).

### 2. [P1] Do not turn absent provider usage into known zero usage

Candidate `live-model-transport.ts:88–90` substitutes zero independently for missing input/output usage. A successful response omitting usage therefore passes `ModelResultV2Schema` as known zero. Root `supervisor.ts:415–439` treats those manufactured numbers as trustworthy, writes `accounting='known'`, does not increment `unknown_calls`, and uses them for token-ceiling acceptance. A response with no usage can thus execute tool calls while concealing uncertainty.

The lifecycle handoff requires trustworthy actual accounting or one unknown-call count. Smallest correction: validate both provider usage counters as safe nonnegative integers without defaults; when unavailable, fail through the existing unknown-accounting path and permit no tools. Separately, valid usage currently disappears when argument parsing/result validation throws: preserve independently validated usage in a bounded error result where possible rather than unnecessarily recording it unknown. Test absent/partial/null/invalid usage and malformed tool arguments with valid usage, observing the supervisor's actual known/unknown counters.

### 3. [P1] Validate provider completion state before constructing a successful result

Candidate `live-model-transport.ts:72–85` defaults absent choices/messages to a no-tool `done`, invents provider/native IDs, defaults missing arguments to `{}`, and chooses `tool_calls` whenever calls exist even if `finish_reason` is `length` or another failure state. Static example: an HTTP 200 JSON body `{}` becomes a valid result with `providerCallId:'provider-call'`, zero usage and `stopReason:'done'`. Independently of missing-usage finding 2, a body with valid ID/usage but an empty choices array also becomes `done`. A length-limited response containing one syntactically valid call becomes executable instead of stopping.

Root `supervisor.ts:435–447` trusts the adapter's normalized stop reason; only `error`/`limit` stop the task before calls are created. Smallest correction: validate a non-streaming provider envelope, real IDs, the expected choice/message and function-call fields before normalization. Map only supported success finishes to success; map truncation/filter/refusal/error to a bounded non-executable error/limit result, preserving trustworthy usage. Do not invent required provider facts. Reject inconsistent tool-bearing completion states before any execution. Test empty choices, missing IDs/arguments, unknown finish, filtered/refused output and length-with-calls. The official API distinguishes `stop`, `length`, `content_filter` and `tool_calls` ([API reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)).

### 4. [P1] Require a valid input-budget preflight before a live request

Candidate `live-model-transport.ts:12,28–30` makes estimation optional and simply sends the request when omitted. The happy-path test at lines 60–63 explicitly uses that path. Root validates the turn's declared limits and JSON size; that does not count the tokens in instructions, transcript and tool schemas. Its later actual-usage check can reject output but cannot undo an over-budget provider invocation. The new `model.ts:16–21` helper also treats NaN or negative estimates as below ceiling because it only performs `>` comparisons.

Smallest correction: require an approved deterministic preflight covering the actual serialized provider input, validate its counters, and refuse before network I/O if the meter is absent/invalid or exceeds either saved-turn or package ceilings. Preserve the injected configuration seam; do not invent a product tokenizer/model/env policy. Blocker D explicitly reserves the tokenizer policy for the owner, so that policy is a prerequisite to claiming usable live readiness. Add no-fetch assertions for absent/invalid estimation and low saved input ceilings. Existing optional callback coverage proves only that a deliberately supplied over-limit number is rejected.

### 5. [P2] Bound and sanitize provider-body parsing before normalization

Candidate `live-model-transport.ts:64–78` reads the complete response with `response.json()` before any byte bound, then parses arbitrary argument strings. Only the fetch promise itself is caught at lines 59–61; body-read, JSON and schema exceptions escape as raw exceptions. The later 128-KiB ModelResult validation cannot bound memory spent reading/parsing the response, and `slice(0,2000)` hides an oversized returned message rather than rejecting it. A compatible endpoint returning an oversized 200 body can allocate/parse arbitrarily large data on the shared control process before validation.

Smallest correction: enforce a documented transport response-byte bound while reading, reject oversized model content rather than silently truncate, and normalize body/argument/schema failures into bounded safe codes. Preserve valid accounting independently as in finding 2. Test streamed oversized bodies, invalid JSON, invalid arguments and body-read rejection. Root currently catches adapter rejection without exposing exception text (`supervisor.ts:495–499`), so this review does **not** claim a demonstrated browser secret leak; the unsafe/unbounded exception boundary is inside this adapter.
